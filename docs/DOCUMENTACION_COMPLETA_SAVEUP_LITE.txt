1. RESUMEN EJECUTIVO Y OBJETIVOS
================================================================================

SaveUp Lite es una aplicacion backend de servicios REST orientada a la gestion 
financiera personal inteligente. Permite a los usuarios registrar ingresos y 
gastos, organizar sus finanzas bajo la popular regla de presupuesto 50/30/20, 
gestionar metas de ahorro con distribucion automatica (Smart-Split), monitorear 
y amortizar deudas en cuotas con calculos en tiempo real, y generar reportes 
exportables estructurados en PDF y CSV.

Aspectos destacados:
- Modelo financiero integral: ingresos, gastos, deudas, metas y presupuestos 
  conectados sin fisuras de integridad. El signo de cada movimiento lo impone su
  tipo (regla canonica) y el saldo es la suma directa de MOVIMIENTO.monto.
- Motor financiero propio (paquete service/finanzas): cuotas francesas, tabla de
  amortizacion, CAE y conversion de tasas, ademas de una imputacion de pagos pura
  (interes -> costo adicional -> capital) que no se persiste.
- Simulador de credito sin persistencia (POST /api/v1/simulaciones/credito): cuota,
  costos, CAE, resumen educativo, tabla de amortizacion y comparacion de plazos.
- Deudas con condiciones de credito (modalidades SIN_INTERES, TASA_CONOCIDA y
  CUOTA_CONOCIDA), ficha enriquecida, cronograma con estado por cuota e historial
  de pagos con su desglose.
- Smart-Split: asignacion automatizada de porcentajes de ahorro a metas al 
  percibir ingresos generales, con vinculo trazable al ingreso de origen.
- Presupuesto 50/30/20 mas limites por categoria con medicion de ejecucion
  (OK / ALERTA / EXCEDIDO) e historial mensual.
- Calculos en tiempo real: saldos de cuenta, montos acumulados por meta, montos 
  pagados y restantes en deudas, y porcentaje de ejecucion presupuestaria.
- Alta compatibilidad de exportacion: PDFs con estilos corporativos listos para 
  impresion y CSVs optimizados con UTF-8 BOM para apertura directa en Excel.
- Despliegue preparado para produccion en contenedores Docker ligeros con 
  mantenimiento activo de disponibilidad mediante GitHub Actions.

2. ARQUITECTURA TECNOLOGICA Y ESTRUCTURA DE CAPAS
================================================================================

El backend sigue una arquitectura clasica por capas (N-Tier Layered Architecture),
combinada con patrones de diseno como Data Transfer Object (DTO) y Strategy:

[Cliente HTTP / Frontend (Ionic, Capacitor, Web)]
                     |
                     v
   [Capa Controladores REST (@RestController)]
     - Recibe peticiones HTTP, valida DTOs de entrada (@Valid).
     - Retorna ResponseEntity con HTTP Status apropiados.
                     |
                     v
     [Capa de Servicios (@Service)]
     - Implementa las reglas de negocio y transacciones (@Transactional).
     - Transforma entidades a DTOs de respuesta para aislar el modelo interno.
     - Aplica el patron Strategy para exportacion de reportes.
                     |
                     v
   [Capa de Repositorios (@Repository / JpaRepository)]
     - Consultas derivadas de Spring Data JPA.
     - Consultas JPQL optimizadas mediante @Query con agregaciones SUM, COUNT.
                     |
                     v
   [Capa de Persistencia / Entidades (@Entity)]
     - Mapeo relacional JPA/Hibernate contra Supabase PostgreSQL.
     - Gestion del ciclo de vida de entidades con @PrePersist.

3. MODELO DE DATOS Y ESQUEMA DE ENTIDADES (JPA / HIBERNATE)
================================================================================

3.1. ENTIDAD USUARIO (Tabla: USUARIO)
--------------------------------------------------------------------------------
Representa al propietario de las cuentas y finanzas.
Campos:
- rut (String, PK, unico): Identificador nacional unico (ej. "12345678-9").
- nombre (String, NOT NULL): Nombre del usuario.
- apellido (String, NOT NULL): Apellido del usuario.
- email (String, NOT NULL, UNIQUE): Direccion de correo electronico.
- contrasena (String, NOT NULL, length=100): Hash BCrypt de la contrasena.
- fechaRegistro (Date, NOT NULL, updatable=false): Fecha y hora de creacion.
Ciclo de vida:
- @PrePersist onCreate(): Si fechaRegistro es nula, inicializa con new Date().

3.2. ENTIDAD CATEGORIA (Tabla: CATEGORIA)
--------------------------------------------------------------------------------
Clasifica los movimientos y los asocia a una regla presupuestaria.
Campos:
- id (Long, PK, Auto-incremental IDENTITY): Identificador de la categoria.
- nombre (String, NOT NULL, UNIQUE): Nombre (ej. "Comida", "Transporte").
- iconId (String): Nombre del icono para la UI (ej. "ic_fastfood", "ic_work").
- colorHex (String): Codigo hexadecimal de color (ej. "#FFC107").
- tipoPresupuesto (Enum TipoPresupuesto): Clasificacion presupuestaria 
  (NECESIDAD, DESEO, AHORRO, OTROS).

3.3. ENTIDAD MOVIMIENTO (Tabla: MOVIMIENTO)
--------------------------------------------------------------------------------
Representa cada transaccion financiera realizada por el usuario.
Campos:
- id (Long, PK, Auto-incremental IDENTITY): Identificador unico de transaccion.
- monto (BigDecimal, NOT NULL): Cantidad monetaria. Positiva para ingresos y retiros 
  de metas; negativa para gastos, pagos de deudas y abonos a metas.
- descripcion (String, NOT NULL, length=100): Detalle descriptivo del movimiento.
- fecha (Date, NOT NULL, updatable=false): Marca de tiempo del movimiento.
- tipoMovimiento (Enum TipoMovimiento, NOT NULL): Naturaleza del movimiento.
- usuario (ManyToOne, NOT NULL, Lazy): Relacion al Usuario dueno del movimiento.
- categoria (ManyToOne, Eager, Nullable): Categoria asignada.
- deuda (ManyToOne, Lazy, Nullable): Deuda vinculada si el tipo es PAGO_DEUDA.
- metaAhorro (ManyToOne, Lazy, Nullable): Meta vinculada si es abono/retiro.
- movimientoOrigen (ManyToOne, Lazy, Nullable, updatable=false): Movimiento que
  origino a este. Smart-Split deja aqui el INGRESO_GENERAL cuyos abonos
  automaticos son este movimiento (T4). Es null en todo movimiento que no
  provenga de Smart-Split, incluido el historico. Inmutable tras la insercion.
Invariante de signo (T1d):
- El signo NO lo decide el cliente ni el productor: lo impone el tipo mediante
  SignoMovimiento. El saldo del usuario es SUM(MOVIMIENTO.monto).
Ciclo de vida:
- @PrePersist onCreate(): Si fecha es nula, inicializa con new Date().
Nota de tipo: monto es BigDecimal (precision 19, escala 2, redondeo HALF_EVEN);
se elimino el uso de Double en los DTOs de movimiento.

3.4. ENTIDAD META_AHORRO (Tabla: META_AHORRO)
--------------------------------------------------------------------------------
Objetivo de ahorro financiero del usuario.
Campos:
- id (Long, PK, Auto-incremental IDENTITY): Identificador unico de la meta.
- nombre (String, NOT NULL, length=100): Titulo o motivo (ej. "Vacaciones").
- montoObjetivo (BigDecimal, Nullable): Monto final deseado. Es nulo en la meta 
  por defecto "Ahorros".
- montoActual (BigDecimal, Default 0.00): Monto total acumulado en la meta.
- fechaLimite (Date, Nullable): Fecha estimada de cumplimiento.
- usuario (ManyToOne, NOT NULL, Lazy): Propietario de la meta.
Metodo auxiliar:
- getMontoActual(): Retorna montoActual != null ? montoActual : BigDecimal.ZERO.

3.5. ENTIDAD DEUDA (Tabla: DEUDA)
--------------------------------------------------------------------------------
Compromiso financiero o pasivo adquirido por el usuario. Desde V3 (T1c) guarda
las condiciones del credito, ademas de las etiquetas y las cuotas ya pagadas.
Campos:
- id (Long, PK, Auto-incremental IDENTITY): Identificador de la deuda.
- nombre (String, NOT NULL, length=100): Titulo (ej. "Credito de Consumo").
- descripcion (String, length=255, Nullable): Informacion adicional.
- montoTotal (BigDecimal, NOT NULL): Monto global a pagar (capital + intereses y
  costos); lo calcula el motor financiero, no lo envia el cliente.
- cantidadCuotas (int, NOT NULL): Total de cuotas pactadas (1-360).
- estado (Enum EstadoDeuda, NOT NULL): PENDIENTE, PAGADA o CANCELADA.
- tipoDeuda (Enum TipoDeuda, NOT NULL, default OTRO): PERSONAL, TIENDA,
  CREDITO_CONSUMO, EDUCACION u OTRO.
- modalidadCalculo (Enum ModalidadCalculo, NOT NULL, default SIN_INTERES):
  SIN_INTERES, TASA_CONOCIDA o CUOTA_CONOCIDA.
- montoCapital (BigDecimal, NOT NULL): Capital sobre el que se calcula.
- gastosIniciales (BigDecimal, NOT NULL, default 0): Gastos cobrados al desembolso.
- costoAdicionalPorCuota (BigDecimal, NOT NULL, default 0): Costo fijo por cuota.
- tasaMensual (BigDecimal, NOT NULL, precision 12 escala 8, default 0): Tasa
  mensual como FRACCION (0.015 = 1,5 %). La capa DTO la expone en porcentaje; el
  motor trabaja con la fraccion.
- valorCuota (BigDecimal, NOT NULL): Cuota calculada o publicada.
- fechaPrimeraCuota (LocalDate, Nullable): Ancla del calendario de vencimientos.
- cuotasPagadasPrevias (int, NOT NULL, default 0): Cuotas ya pagadas antes de
  usar la app (se cuentan como completas en la imputacion).
- montoPagadoPrevio (BigDecimal, NOT NULL, default 0): Suma (cuota + costo
  adicional) de esas cuotas previas.
- cargaAnualEquivalente (BigDecimal, NOT NULL, precision 10 escala 4, default 0):
  CAE referencial como fraccion.
- costoTotalCredito (BigDecimal, NOT NULL): montoTotal + gastosIniciales.
- fechaCreacion (Date, NOT NULL, updatable=false): Fecha de ingreso de la deuda.
- usuario (ManyToOne, NOT NULL, Lazy): Usuario deudor.
Ciclo de vida:
- @PrePersist onCreate(): Establece fecha actual y estado PENDIENTE por defecto.
Notas:
- El cliente ya no envia montoTotal ni cantidadCuotas cuando usa el bloque
  "condiciones" (condiciones de credito); el motor los deriva.
- Las tasas se guardan como fraccion; la conversion porcentaje <-> fraccion vive
  en dto/PorcentajeTasa (regla 40).

3.6. ENTIDAD CONFIGURACION_PRESUPUESTO (Tabla: CONFIGURACION_PRESUPUESTO)
--------------------------------------------------------------------------------
Configuracion del esquema de distribucion de ingresos del usuario (regla 50/30/20).
El presupuesto actua como guia de control y visualizacion de gastos (Necesidades /
Deseos / Ahorro); la ejecucion fisica de abonos automaticos a metas es opcional.
Campos:
- id (Long, PK, Auto-incremental IDENTITY): Identificador de la configuracion.
- usuario (OneToOne, NOT NULL): Usuario asociado (relacion 1 a 1).
- porcentajeNecesidades (BigDecimal, NOT NULL): Porcentaje asignado (ej. 50.00).
- porcentajeDeseos (BigDecimal, NOT NULL): Porcentaje asignado (ej. 30.00).
- porcentajeAhorro (BigDecimal, NOT NULL): Porcentaje asignado (ej. 20.00).
- activo (Boolean, NOT NULL, default=true): Indica si la configuracion esta habilitada.
- automatizarAhorroEnMetas (Boolean, NOT NULL, default=false): Bandera de desacoplamiento.
  * false (por defecto): El presupuesto actua solo como guia visual 50/30/20. El dinero
    permanece 100% liquido en el saldo principal; no se generan sub-movimientos ABONO_META.
  * true: Smart-Split ejecuta la distribucion fisica del porcentaje de ahorro hacia las
    metas configuradas, creando movimientos ABONO_META y debitando el saldo principal.
Ciclo de vida (@PrePersist / @PreUpdate):
- Si activo es null, se inicializa en true.
- Si automatizarAhorroEnMetas es null, se inicializa en false (seguridad defensiva).

3.7. ENTIDAD ASIGNACION_META_PRESUPUESTO (Tabla: ASIGNACION_META_PRESUPUESTO)
--------------------------------------------------------------------------------
Sub-distribucion del porcentaje de ahorro hacia metas individuales especificas.
Campos:
- id (Long, PK, Auto-incremental IDENTITY): Identificador de la asignacion.
- configuracion (ManyToOne, NOT NULL, Lazy): Configuracion a la que pertenece.
- meta (ManyToOne, NOT NULL, Eager): Meta de ahorro beneficiaria.
- porcentajeAsignacion (BigDecimal, NOT NULL): Fraccion del ahorro total (ej. 60.00%).

3.8. ENTIDAD PRESUPUESTO_CATEGORIA (Tabla: PRESUPUESTO_CATEGORIA) [NUEVA - V6/T5]
--------------------------------------------------------------------------------
Limite de gasto MENSUAL y recurrente de un usuario sobre una categoria. El monto
se reutiliza mes a mes (no esta atado a un periodo concreto) y permite medir la
ejecucion real (gastado vs. limite). Complementa al reparto 50/30/20 por tipo.
Campos:
- id (Long, PK, Auto-incremental IDENTITY): Identificador del limite.
- usuario (ManyToOne, NOT NULL, Lazy): Propietario del limite.
- categoria (ManyToOne, NOT NULL, Eager): Categoria acotada.
- limiteMensual (BigDecimal, NOT NULL, precision 19 escala 2): Tope mensual;
  siempre mayor a 0 (tambien por CHECK en la BD).
Restricciones:
- UNIQUE(usuario, categoria): un solo limite por usuario y categoria.
- CHECK chk_presup_cat_limite: limite_mensual > 0.
- RLS habilitado (V6 y V8).

4. CATALOGO COMPLETO DE ENUMS
================================================================================

4.1. Enum: TipoMovimiento
-------------------------
Ubicacion: com.example.saveup.model.enums.TipoMovimiento
Valores:
- INGRESO_GENERAL : Entrada de dinero principal (sueldos, rentas, transferencias).
                    Puede disparar el algoritmo Smart-Split si asi se indica.
- GASTO_GENERAL   : Salida ordinaria de dinero (alimentacion, ocio, cuentas).
- PAGO_DEUDA      : Amortizacion de una cuota o monto de una deuda existente.
- ABONO_META      : Traslado de dinero desde el saldo principal hacia una meta.
- RETIRO_META     : Rescate de dinero desde una meta hacia el saldo principal.

4.2. Enum: EstadoDeuda
----------------------
Ubicacion: com.example.saveup.model.enums.EstadoDeuda
Valores:
- PENDIENTE : La deuda esta vigente y admite abonos/pagos de cuotas.
- PAGADA    : El total pagado ha igualado o superado el montoTotal.
- CANCELADA : La deuda fue dada de baja de forma manual por el usuario.

4.3. Enum: TipoPresupuesto
--------------------------
Ubicacion: com.example.saveup.model.enums.TipoPresupuesto
Valores:
- NECESIDAD : Gastos vitales imprescindibles (supermercado, arriendo, luz, salud).
              Base del 50% de la regla presupuestaria.
- DESEO     : Gastos de ocio, placer y estilo de vida (cine, salidas, ropa, viajes).
              Base del 30% de la regla presupuestaria.
- AHORRO    : Categorias que representan acumulacion de capital o inversiones.
              Base del 20% de la regla presupuestaria.
- OTROS     : Entradas u otros conceptos que no clasifican como gasto 
              presupuestario estandar.

4.4. Enum: TipoDeuda  [NUEVO - V3]
------------------------
Ubicacion: com.example.saveup.model.enums.TipoDeuda
Valores:
- PERSONAL, TIENDA, CREDITO_CONSUMO, EDUCACION, OTRO.
- Etiqueta de la deuda; no altera el calculo. Un valor nulo se normaliza a OTRO.

4.5. Enum: ModalidadCalculo  [NUEVO - T1a/T1c]
------------------------
Ubicacion: com.example.saveup.model.enums.ModalidadCalculo
Valores:
- SIN_INTERES    : No admite tasas ni valor de cuota; cuota = capital / n.
- TASA_CONOCIDA  : Exige exactamente una de tasaMensual o tasaAnualEfectiva.
- CUOTA_CONOCIDA : Exige valorCuota > 0 y NO admite ninguna tasa.

4.6. Enum: ModoPago  [NUEVO - T2]
------------------------
Ubicacion: com.example.saveup.model.enums.ModoPago
Valores:
- CUOTA_CALCULADA    : El monto enviado se ignora; se cobra lo que falta de la
                       proxima cuota impaga (cuota + costo adicional).
- MONTO_PERSONALIZADO: Se cobra el monto enviado (obligatorio y > 0). Es el
                       valor por defecto para no romper clientes existentes.
No se persiste: solo decide con que monto se registra el movimiento PAGO_DEUDA.

4.7. Enum: EstadoEjecucion  [NUEVO - T5]
------------------------
Ubicacion: com.example.saveup.model.enums.EstadoEjecucion
Valores (derivados del porcentaje usado):
- OK       : porcentaje < 80 (UMBRAL_ALERTA).
- ALERTA   : porcentaje >= 80 y < 100.
- EXCEDIDO : porcentaje >= 100 (UMBRAL_EXCEDIDO).
Metodo auxiliar: desdePorcentaje(BigDecimal) compara con compareTo (80 y 80.00
son iguales); un porcentaje nulo se trata como OK (sin gasto).

5. CATALOGO EXHAUSTIVO DE DTOs (DATA TRANSFER OBJECTS)
================================================================================

5.1. UsuarioRegistroDTO
- Paquete: com.example.saveup.dto
- Proposito: Payload para recepcion de datos de registro de nuevos usuarios.
- Campos y Validaciones:
  * rut (String): @NotBlank, @Pattern(regexp = "^\\d{7,8}-[\\dkK]{1}$")
  * nombre (String): @NotBlank, @Size(min = 2, max = 50)
  * apellido (String): @NotBlank, @Size(min = 2, max = 50)
  * email (String): @NotBlank, @Email
  * contrasena (String): @NotBlank, @Size(min = 8, max = 20), 
                        @Pattern(regexp = "^(?=.*[A-Za-z])(?=.*\\d).*$")

5.2. UsuarioLoginDTO
- Proposito: Payload de credenciales para iniciar sesion.
- Campos:
  * email (String): @NotBlank, @Email
  * contrasena (String): @NotBlank

5.3. MovimientoRegistroDTO
- Proposito: Entrada para asentar una nueva transaccion financiera.
- Campos:
  * monto (BigDecimal): @NotNull, @Digits(integer=17, fraction=2).
  * descripcion (String): @NotBlank
  * tipoMovimiento (TipoMovimiento): @NotNull. POST solo acepta INGRESO_GENERAL,
    GASTO_GENERAL y PAGO_DEUDA (ABONO_META y RETIRO_META se rechazan con 400).
  * deudaId (Long, opcional): Requerido exclusivamente si es PAGO_DEUDA.
  * metaId (Long, opcional): Meta vinculada para abonos o retiros.
  * categoriaId (Long, opcional): Categoria asignada al movimiento.
  * aplicarPresupuesto (Boolean, default false): Activa el Smart-Split.
  (Nota: usuarioRut fue removido; la identidad se extrae estrictamente del token JWT).
  (Nota: el monto viaja en positivo; el signo lo impone SignoMovimiento segun el tipo).

5.4. MovimientoResponseDTO
- Proposito: Datos de salida al consultar un movimiento o confirmar su creacion.
- Campos:
  * id (Long)
  * monto (BigDecimal): valor canonico (negativo para gastos, pagos y abonos).
  * descripcion (String)
  * fecha (Date)
  * tipoMovimiento (TipoMovimiento)
  * categoria (CategoriaDTO)
- Metodo estatico from(Movimiento): mapper compartido por todos los productores de
  movimientos (MovimientoService, DeudaService, MetaAhorroService, SmartSplit).

5.5. CategoriaDTO
- Proposito: Transporte liviano de informacion de categorias con metadatos de UI.
- Campos:
  * id (Long)
  * nombre (String)
  * iconId (String)
  * colorHex (String)
  * tipoPresupuesto (TipoPresupuesto)

5.6. MetaAhorroCreacionDTO
- Proposito: Creacion o edicion de una meta de ahorro.
- Campos:
  * nombre (String): @NotBlank
  * montoObjetivo (BigDecimal): @Positive (opcional), @Digits(17,2)
  * fechaLimite (Date): @Future (opcional)
  (Nota: usuarioRut fue removido; la identidad se extrae del contexto de seguridad).

5.7. MetaAhorroResponseDTO
- Proposito: Informacion completa de la meta devuelta a la aplicacion cliente.
- Campos:
  * id (Long)
  * nombre (String)
  * montoObjetivo (BigDecimal, Nullable)
  * fechaLimite (Date)
  * montoActual (BigDecimal): saldo acumulado persistido y calculado en el servicio.

5.8. AbonoRetiroDTO
- Proposito: Ejecucion de inyeccion o extraccion voluntaria de dinero en una meta.
- Campos:
  * monto (BigDecimal): @NotNull, @Positive, @Digits(17,2)
  * descripcion (String): @NotBlank

5.9. DeudaCreacionDTO
- Proposito: Alta o actualizacion de compromisos de deuda.
- Campos:
  * nombre (String): @NotBlank
  * descripcion (String, opcional)
  * tipoDeuda (TipoDeuda, opcional; nulo -> OTRO)
  * cuotasPagadasPrevias (Integer, default 0): @Min(0)
  * condiciones (CondicionesCreditoInput, @Valid, opcional): bloque de condiciones
    de credito (modalidad, montoCapital, tasas/cuota, fechas, costos).
  * montoTotal (BigDecimal, opcional): @Positive, @Digits(17,2). Compatibilidad.
  * cantidadCuotas (Integer, opcional): @Positive.
  - Si viene "condiciones", el motor deriva montoTotal/cuotas/tasas.
  - Sin "condiciones", se exige montoTotal y cantidadCuotas (modalidad SIN_INTERES).
  (Nota: usuarioRut fue removido; la identidad se extrae del contexto de seguridad).

5.10. DeudaResponseDTO
- Proposito: Respuesta detallada de una deuda. Es un DTO de datos: los campos
  derivados los calcula DeudaService en memoria tras la proyeccion JPQL
  (motor financiero + calendario + imputacion), sin consultas extra por deuda.
- Campos:
  * id, nombre, descripcion
  * tipoDeuda (TipoDeuda), modalidadCalculo (ModalidadCalculo)
  * montoCapital (BigDecimal)
  * tasaMensual (BigDecimal): tasa mensual EN PORCENTAJE. Se renombro desde
    "tasaMensualPorcentaje" (ver nota de compatibilidad abajo).
  * tasaAnualEfectiva (BigDecimal): en porcentaje, calculada como (1+m)^12 - 1.
  * tasaMensualFraccion (BigDecimal): fraccion cruda del motor; oculta con
    @JsonIgnore.
  * valorCuota, gastosIniciales, costoAdicionalPorCuota, costoTotalCredito,
    cargaAnualEquivalente (porcentaje)
  * fechaPrimeraCuota, fechaUltimaCuota, cuotasPagadasPrevias, montoPagadoPrevio
  * montoTotal (BigDecimal), cantidadCuotas (int), estado (EstadoDeuda),
    fechaCreacion (Date)
  * montoPagadoReal (BigDecimal): solo los pagos reales, sin las cuotas previas.
  * montoPagado (BigDecimal): montoPagadoPrevio + montoPagadoReal.
  * montoRestante / totalPorPagar (BigDecimal): montoTotal - montoPagado.
  * saldoCapital (BigDecimal): montoCapital - capital imputado (aproxima lo que
    costaria liquidar hoy; NO incluye el interes devengado del mes en curso).
  * cuotasPagadas (int): cuotas PAGADA segun la imputacion (incluye las previas).
  * proximaCuotaNumero (Integer), proximaCuotaMontoPendiente (BigDecimal),
    proximaFechaVencimiento (LocalDate); null si no queda cuota o no hay calendario.
  * interesesPagados (BigDecimal): interes imputado a pagos y cuotas previas.
- Los campos derivados quedan en null si una deuda no se puede recalcular; el
  listado sigue funcionando.
- Compatibilidad: el JSON expone "tasaMensual" en lugar del antiguo
  "tasaMensualPorcentaje". Cualquier cliente que lea la clave vieja debe cambiar.

5.11. PagoDeudaDTO
- Proposito: Registro de abono o pago a una cuota de una deuda activa.
- Campos:
  * monto (BigDecimal, opcional): @Digits(17,2). Obligatorio solo en
    MONTO_PERSONALIZADO; en CUOTA_CALCULADA se ignora.
  * descripcion (String): @NotBlank
  * modoPago (ModoPago, default MONTO_PERSONALIZADO): CUOTA_CALCULADA o
    MONTO_PERSONALIZADO.

5.12. ConfiguracionPresupuestoRequestDTO
- Proposito: Establecer o modificar los parametros del presupuesto 50/30/20 y la
  opcion de automatizacion de abonos a metas.
- Campos y Validaciones:
  * porcentajeNecesidades (BigDecimal): @NotNull, @DecimalMin("0.0"), @DecimalMax("100.0")
  * porcentajeDeseos (BigDecimal): @NotNull, @DecimalMin("0.0"), @DecimalMax("100.0")
  * porcentajeAhorro (BigDecimal): @NotNull, @DecimalMin("0.0"), @DecimalMax("100.0")
  * activo (Boolean): Opcional, default true.
  * automatizarAhorroEnMetas (Boolean): Opcional, default false.
    - false: El presupuesto funciona como guia visual; ningun ABONO_META se genera.
    - true: Smart-Split ejecutara distribucion fisica al registrar un INGRESO_GENERAL
            con aplicarPresupuesto=true.
  * asignaciones (List<AsignacionPresupuestoDTO>): @Valid. Lista de sub-distribuciones
    del porcentaje de ahorro hacia metas individuales. Requerido solo si
    automatizarAhorroEnMetas=true y se desea distribucion granular por meta.

5.13. AsignacionPresupuestoDTO
- Proposito: Declarar que fraccion del ahorro se destinara a una meta concreta.
- Campos y Validaciones:
  * metaId (Long): @NotNull. ID de la meta de ahorro beneficiaria.
  * porcentaje (BigDecimal): @NotNull, @DecimalMin("0.0"), @DecimalMax("100.0").
    Fraccion del monto total de ahorro a derivar (ej. 60.0 -> 60% del ahorro va a esa meta).

5.14. EjecucionPresupuestoDTO
- Proposito: Comparativa mensual de presupuesto proyectado vs ejecucion real,
  incluyendo metricas de ahorro y el estado de automatizacion configurado.
- Campos:
  * presupuestoNecesidades (BigDecimal)  : (Total Ingresos * % Necesidades)
  * gastoNecesidades (BigDecimal)       : Suma real de gastos clasificados como NECESIDAD
  * presupuestoDeseos (BigDecimal)      : (Total Ingresos * % Deseos)
  * gastoDeseos (BigDecimal)            : Suma real de gastos clasificados como DESEO
  * presupuestoAhorro (BigDecimal)      : (Total Ingresos * % Ahorro) — monto objetivo
  * ahorroRealizado (BigDecimal)        : Suma de egresos ABONO_META del mes (ahorro fisico
                                          efectivamente movido a metas via Smart-Split o manual)
  * totalIngresos (BigDecimal)          : Total acumulado de INGRESO_GENERAL del mes
  * porcentajeNecesidadesConfigurado (BigDecimal): % configurado para Necesidades
  * porcentajeDeseosConfigurado (BigDecimal)     : % configurado para Deseos
  * porcentajeAhorroConfigurado (BigDecimal)     : % configurado para Ahorro
  * automatizarAhorroEnMetas (Boolean)       : Refleja si la automatizacion fisica
                                               de abonos a metas esta habilitada.

5.15. PageResponseDTO<T>
- Proposito: Contenedor generico estandarizado para respuestas con paginacion.
- Campos:
  * content (List<T>)
  * currentPage (int)
  * totalItems (long)
  * totalPages (int)

5.16. CondicionesCreditoInput  [NUEVO - T1c]
- Proposito: Entrada de condiciones de credito desde la API. Las tasas vienen en
  PORCENTAJE (0-100) y los campos son opcionales; ResolutorCondiciones valida y
  normaliza.
- Campos:
  * modalidad (ModalidadCalculo): @NotNull
  * montoCapital (BigDecimal): @NotNull, @DecimalMin("0.01")
  * cantidadCuotas (Integer), fechaPrimeraCuota / fechaUltimaCuota (LocalDate)
  * tasaMensual (BigDecimal): porcentaje
  * tasaAnualEfectiva (BigDecimal): porcentaje
  * valorCuota (BigDecimal), gastosIniciales (BigDecimal),
    costoAdicionalPorCuota (BigDecimal)
- Metodos tasaMensualFraccion() / tasaAnualEfectivaFraccion(): delegan en
  dto/PorcentajeTasa. La conversion porcentaje -> fraccion vive en el DTO, nunca
  en el motor (regla 40).

5.17. SimulacionCreditoRequestDTO  [NUEVO - T1b]
- Proposito: Peticion del simulador de credito (sin persistencia).
- Campos:
  * modalidad (ModalidadCalculo): @NotNull
  * montoCapital (BigDecimal): @NotNull, @DecimalMin("0.01")
  * cantidadCuotas (Integer), fechaPrimeraCuota / fechaUltimaCuota (LocalDate)
  * tasaMensual (BigDecimal): porcentaje (0-100)
  * tasaAnualEfectiva (BigDecimal): porcentaje
  * valorCuota (BigDecimal), gastosIniciales (BigDecimal),
    costoAdicionalPorCuota (BigDecimal)
  * ingresoMensual (BigDecimal, opcional): base del resumen educativo
  * cantidadCuotasAlternativas (List<Integer>, opcional): hasta 5 plazos
  * incluirTabla (Boolean, default true): si false omite la tabla de amortizacion

5.18. SimulacionCreditoResponseDTO  [NUEVO - T1b]
- Proposito: Resultado del simulador: cuota, costos, CAE, resumen educativo,
  tabla y comparacion de plazos. @JsonInclude(NON_NULL).
- Campos:
  * condiciones (CondicionesSimulacionDTO): modalidad, montoCapital,
    cantidadCuotas, fechas y tasas normalizadas (en porcentaje)
  * valorCuota, montoTotal, gastosIniciales, costoTotalCredito,
    interesesYCostos, cargaAnualEquivalente (porcentaje)
  * resumenEducativo (ResumenEducativoDTO): costoPorCada100,
    porcentajeSobreCapital, porcentajeInteresesYCostos,
    porcentajeIngresoComprometido (null si no se envio ingresoMensual)
  * tablaAmortizacion (List<CuotaSimulacionDTO>)
  * comparacionPlazos (List<ComparacionPlazoDTO>)
  * advertencias (List<String>): aviso CAE referencial y, si la cuota compromete
    mas del 30% del ingreso, aviso de sobreendeudamiento
- Sub-DTO CuotaSimulacionDTO: numero, fechaVencimiento, cuota, capital, interes,
  costoAdicional, saldo y (solo para deudas reales) estado, montoPagado, previa.
  El mapper compartido from(tabla, fechas) lo usan el simulador y el detalle de
  deuda.

5.19. PagoDeudaResponseDTO  [NUEVO - T3]
- Proposito: Un pago real de una deuda con su desglose. El desglose NO se
  persiste: DeudaService lo recalcula con ImputacionPagos como la imputacion
  acumulada tras ese pago menos la del anterior.
- Campos: id (Long), fecha (Date), monto (BigDecimal, positivo), capital,
  interes, costos, descripcion (String).

5.20. MovimientoFiltroDTO  [NUEVO - T4]
- Proposito: Filtros opcionales de GET /api/v1/movimientos/paginados/me.
- Campos (todos opcionales):
  * desde / hasta (LocalDate, ISO inclusivos; no puede haber desde > hasta)
  * tipoMovimiento (TipoMovimiento)
  * categoriaId (Long)
  * montoMin / montoMax (BigDecimal): comparan contra la magnitud (valor
    absoluto) del monto; no pueden ser negativos ni montoMin > montoMax
  * q (String): busqueda case-insensitive en descripcion

5.21. MovimientoEdicionDTO  [NUEVO - T4]
- Proposito: Edicion parcial de un movimiento (PUT /api/v1/movimientos/{id}). La
  fecha NO es editable; el tipo tampoco se cambia aqui. Se aplican solo los
  campos no nulos.
- Campos: monto (BigDecimal, @Digits(17,2)), descripcion (String, @Size(max=100)),
  categoriaId (Long).

5.22. ConfiguracionPresupuestoResponseDTO  [NUEVO - T5]
- Proposito: Configuracion 50/30/20 expuesta por la API. Sustituye a la entidad
  JPA en la respuesta para no filtrar el modelo de persistencia.
- Campos: id (Long), usuarioRut (String), porcentajeNecesidades, porcentajeDeseos,
  porcentajeAhorro (BigDecimal), activo (Boolean), automatizarAhorroEnMetas
  (Boolean).

5.23. PresupuestoCategoriaRequestDTO / PresupuestoCategoriaItemDTO  [NUEVO - T5]
- Proposito: Cuerpo e items del PUT /api/v1/presupuestos/categorias/me (reemplaza el
  conjunto completo de limites). Se envuelve la lista en un DTO para que @Valid
  valide cada item.
- PresupuestoCategoriaItemDTO: categoriaId (Long, @NotNull), limiteMensual
  (BigDecimal, @NotNull, @Positive).

5.24. PresupuestoCategoriaDTO  [NUEVO - T5]
- Proposito: Item de respuesta con los limites del usuario.
- Campos: categoriaId (Long), categoria (String), limiteMensual (BigDecimal).

5.25. EjecucionCategoriaDTO  [NUEVO - T5]
- Proposito: Ejecucion (gastado vs. limite) de una categoria en un mes.
- Campos: categoriaId (Long), categoria (String), limite (BigDecimal), gastado
  (BigDecimal, suma en valor absoluto de GASTO_GENERAL y PAGO_DEUDA del mes),
  porcentajeUsado (BigDecimal), estado (EstadoEjecucion).

5.26. HistorialPresupuestoDTO  [NUEVO - T5]
- Proposito: Ejecucion general 50/30/20 de un mes dentro del historial.
- Campos: anio (Integer), mes (Integer), ejecucion (EjecucionPresupuestoDTO).

5.27. PorcentajeTasa  [NUEVO - T0/regla 40]
- Proposito: Conversion entre la fraccion del motor (0.015 = 1,5 %) y el
  porcentaje de los DTO (1.5). Centraliza la aritmetica *100 / 100 para que no se
  repita por el codigo. Clase utilitaria final sin instancias.
- Metodos: aPorcentaje(fraccion, escala) y aFraccion(porcentaje); devuelven null
  si la entrada es null.

6. MAPA COMPLETO DE ENDPOINTS REST

--------------------------------------------------------------------------------
MODULO: USUARIOS (/api/v1/usuarios)
--------------------------------------------------------------------------------
1. POST /api/v1/usuarios/register (PÚBLICO)
   - Descripcion: Registra un usuario y le crea su meta por defecto "Ahorros".
   - Body: UsuarioRegistroDTO (JSON)
   - Respuestas:
     * 201 Created: {"message": "Usuario registrado exitosamente"}
     * 409 Conflict: {"error": "El RUT ingresado ya está registrado."} o Correo
     * 500 Internal Server Error: {"error": "..."}

2. POST /api/v1/usuarios/login (PÚBLICO)
   - Descripcion: Autentica credenciales mediante BCrypt y retorna el token JWT firmado.
   - Body: UsuarioLoginDTO (JSON)
   - Respuestas:
     * 200 OK: {"token": "eyJhbGci..."}
     * 401 Unauthorized: {"error": "Credenciales inválidas."}

3. GET /api/v1/usuarios/me (PROTEGIDO)
   - Descripcion: Obtiene el perfil completo del usuario autenticado (sin contraseña).
   - Cabecera: Authorization: Bearer <token>
   - Respuestas:
     * 200 OK: Entidad Usuario (con contrasena null)
     * 401 Unauthorized / 403 Forbidden

--------------------------------------------------------------------------------
MODULO: SALDOS (/api/v1/saldos)
--------------------------------------------------------------------------------
4. GET /api/v1/saldos/me (PROTEGIDO - Implicit Context)
   - Descripcion: Retorna el saldo neto acumulado del usuario autenticado.
   - Cabecera: Authorization: Bearer <token>
   - Respuestas:
     * 200 OK: {"saldo": 150000.0}

--------------------------------------------------------------------------------
MODULO: MOVIMIENTOS (/api/v1/movimientos)
--------------------------------------------------------------------------------
5. POST /api/v1/movimientos (PROTEGIDO)
   - Descripcion: Registra un movimiento. usuarioRut es opcional (se infiere del token).
     Acepta solo INGRESO_GENERAL, GASTO_GENERAL y PAGO_DEUDA; ABONO_META y
     RETIRO_META se rechazan con 400 (se crean desde /api/v1/metas). El signo lo
     impone el tipo (SignoMovimiento). Soporta Smart-Split automático si es
     INGRESO_GENERAL y aplicarPresupuesto=true.
   - Body: MovimientoRegistroDTO (JSON)
   - Respuestas:
     * 201 Created: MovimientoResponseDTO
     * 400 Bad Request: tipo no registrable o monto nulo/cero
     * 409 Conflict: sobrepago o deuda no PENDIENTE (pagos delegados a DeudaService)

6. GET /api/v1/movimientos/me (PROTEGIDO - Implicit Context)
   - Descripcion: Obtiene movimientos del usuario autenticado. Permite ?limit=N.
   - Respuestas:
     * 200 OK: List<MovimientoResponseDTO>

7. GET /api/v1/movimientos/paginados/me (PROTEGIDO - Implicit Context)
   - Descripcion: Historial paginado del usuario autenticado. Filtros opcionales
     (T4): ?page=0&size=50&desde&hasta&tipoMovimiento&categoriaId&montoMin&montoMax&q.
     desde/hasta son ISO inclusivos; montoMin/montoMax comparan contra el valor
     absoluto; q busca en descripcion (case-insensitive). Siempre filtra por el
     RUT del token.
   - Respuestas:
     * 200 OK: PageResponseDTO<MovimientoResponseDTO>
     * 400 Bad Request: desde>hasta, montos negativos o montoMin>montoMax

8. PUT /api/v1/movimientos/{id} (PROTEGIDO - Edicion T4)
   - Descripcion: Edicion parcial (descripcion, monto y/o categoriaId; la fecha y
     el tipo no cambian). El monto se reescribe con SignoMovimiento. Solo aplica a
     INGRESO_GENERAL y GASTO_GENERAL sin deuda ni meta; el resto se modifica desde
     su modulo (409). Un ingreso con abonos de Smart-Split vinculados no se edita (409).
   - Body: MovimientoEdicionDTO (JSON)
   - Respuestas:
     * 200 OK: MovimientoResponseDTO
     * 403 Forbidden: movimiento de otro usuario
     * 404 / 409 segun corresponda

9. DELETE /api/v1/movimientos/{id} (PROTEGIDO - T4)
    - Descripcion: Elimina un movimiento propio con las mismas reglas que la
      edicion (tipos permitidos y sin movimientos derivados).
    - Respuestas:
      * 204 No Content
      * 403 / 404 / 409 segun corresponda

--------------------------------------------------------------------------------
MODULO: CATEGORIAS (/api/v1/categorias)
--------------------------------------------------------------------------------
10. GET /api/v1/categorias (PROTEGIDO)
    - Descripcion: Obtiene el catálogo de categorías con colores, iconos y tipo.
    - Respuestas:
      * 200 OK: List<CategoriaDTO>

--------------------------------------------------------------------------------
MODULO: METAS DE AHORRO (/api/v1/metas)
--------------------------------------------------------------------------------
11. POST /api/v1/metas (PROTEGIDO)
    - Descripcion: Crea una meta para el usuario autenticado (usuarioRut opcional).
    - Body: MetaAhorroCreacionDTO (JSON)
    - Respuestas:
      * 201 Created: MetaAhorroResponseDTO

12. GET /api/v1/metas/me (PROTEGIDO - Implicit Context)
    - Descripcion: Lista las metas del usuario autenticado.
    - Respuestas:
      * 200 OK: List<MetaAhorroResponseDTO>

13. POST /api/v1/metas/{metaId}/abonar (PROTEGIDO - Valida propiedad de la meta)
14. POST /api/v1/metas/{metaId}/retirar (PROTEGIDO - Valida propiedad de la meta)
15. PUT /api/v1/metas/{metaId} (PROTEGIDO - Valida propiedad de la meta)
16. DELETE /api/v1/metas/{metaId} (PROTEGIDO - Valida propiedad, reembolso a saldo)

--------------------------------------------------------------------------------
MODULO: DEUDAS (/api/v1/deudas)
--------------------------------------------------------------------------------
17. POST /api/v1/deudas (PROTEGIDO)
    - Descripcion: Registra deuda para el usuario autenticado (identidad obtenida del token).
      Acepta el bloque "condiciones" (motor financiero) o, por compatibilidad,
      montoTotal + cantidadCuotas.
    - Body: DeudaCreacionDTO (JSON)
    - Respuestas:
      * 201 Created: DeudaResponseDTO
      * 400 Bad Request: condiciones invalidas (CalculoFinancieroException)

18. GET /api/v1/deudas/me (PROTEGIDO - Implicit Context)
    - Descripcion: Lista deudas con cálculo en tiempo real optimizado mediante proyección JPQL (evita N+1).
    - Respuestas:
      * 200 OK: List<DeudaResponseDTO>

19. GET /api/v1/deudas/{deudaId} (PROTEGIDO - T3)
    - Descripcion: Devuelve la ficha enriquecida de una deuda. Valida propiedad
      (ajena -> 403).
    - Respuestas: 200 OK: DeudaResponseDTO; 404 / 403

20. GET /api/v1/deudas/{deudaId}/amortizacion (PROTEGIDO - T3)
    - Descripcion: Cronograma reconstruido sin persistir. Cada cuota lleva estado
      (PAGADA | PARCIAL | PENDIENTE), montoPagado y previa segun la imputacion.
    - Respuestas: 200 OK: List<CuotaSimulacionDTO>

21. GET /api/v1/deudas/{deudaId}/pagos (PROTEGIDO - T3)
    - Descripcion: Historial de pagos reales, paginado (?page&size) y en orden
      fecha desc, con desglose capital/interes/costos calculado en memoria.
    - Respuestas:
      * 200 OK: PageResponseDTO<PagoDeudaResponseDTO>
      * 400 Bad Request: page < 0 o size < 1

22. POST /api/v1/deudas/{deudaId}/pagar (PROTEGIDO - Valida propiedad de la deuda)
    - Descripcion: Unico productor de PAGO_DEUDA. modoPago CUOTA_CALCULADA cobra lo
      que falta de la proxima cuota impaga; MONTO_PERSONALIZADO exige monto > 0.

7.1. CAPA DE SERVICIOS (Lógica de Negocio)
--------------------------------------------------------------------------------
* UsuarioService
  - registrarUsuario(UsuarioRegistroDTO): Valida duplicidad, aplica BCrypt, 
    persiste al usuario y crea la meta base "Ahorros" de forma transaccional.
  - autenticarUsuario(UsuarioLoginDTO): Verifica contrasena con BCrypt y 
    arroja BadCredentialsException ante fallos.

* MovimientoService
  - registrarMovimiento(MovimientoRegistroDTO): Toma la identidad del token,
    valida que el tipo sea registrable (INGRESO_GENERAL, GASTO_GENERAL,
    PAGO_DEUDA), aplica SignoMovimiento y guarda. Para PAGO_DEUDA delega en
    DeudaService.registrarPago. Si es INGRESO_GENERAL con aplicarPresupuesto=true,
    guarda el ingreso PRIMERO y luego invoca Smart-Split (asi conoce su id).
  - obtenerMovimientosPorUsuario(String rut, Integer limit): Consulta movimientos
    ordenados con soporte de limite.
  - obtenerSaldoActual(String rut): Ejecuta la agregacion de saldo neto.
  - obtenerMovimientosPaginados(String rut, Pageable, MovimientoFiltroDTO): arma
    una Specification (MovimientoSpecifications.conFiltros) con el RUT obligatorio
    y los filtros opcionales; valida rango (400).
  - editarMovimiento(Long id, MovimientoEdicionDTO): edicion parcial propia; solo
    INGRESO_GENERAL/GASTO_GENERAL sin deuda ni meta y sin abonos derivados (409);
    reescribe el monto con SignoMovimiento.
  - eliminarMovimiento(Long id): mismas validaciones que la edicion y borra.

* SmartSplitProcessor (com.example.saveup.service.SmartSplitProcessor)
  - procesarDistribucion(Movimiento movimientoIngreso, BigDecimal montoIngreso):
    Servicio de dominio especializado que desacopla el algoritmo Smart-Split de
    MovimientoService. Recibe el ingreso ya persistido (con id y usuario).
    Implementa el modelo de automatizacion opcional de metas:
    * Condicion de ejecucion (triple AND): config.activo == true
      AND config.automatizarAhorroEnMetas == true
      AND config.porcentajeAhorro > 0.
    * Si la condicion se cumple: Calcula montoAhorro = ingreso * (%ahorro / 100),
      itera sobre asignaciones de metas, genera un Movimiento ABONO_META por cada
      meta (monto negativo via SignoMovimiento, categoria 'Ahorro'), le deja el
      vinculo movimientoOrigen = ingreso (T4) y actualiza meta.montoActual. El
      residuo de redondeo se asigna a la ultima asignacion.
    * Si la condicion NO se cumple (automatizarAhorroEnMetas=false o config inactiva):
      No se genera ningun sub-movimiento ni debito adicional. El 100% del ingreso
      permanece liquido en el saldo principal del usuario. El presupuesto actua
      exclusivamente como guia visual de control (50/30/20) sin efectos contables.

* MetaAhorroService
  - crearMeta(MetaAhorroCreacionDTO): Inicializa una meta de ahorro.
  - obtenerMetasPorUsuario(String rut): Lista de metas con saldos.
  - realizarAbono(Long metaId, AbonoRetiroDTO): Valida propiedad, aplica
    SignoMovimiento (ABONO_META negativo), abona a la meta con categoria "Ahorro".
  - realizarRetiro(Long metaId, AbonoRetiroDTO): Valida fondos suficientes,
    aplica SignoMovimiento (RETIRO_META positivo) y reintegra al saldo principal.
  - eliminarMeta(Long metaId): Protege la meta por defecto, devuelve los fondos
    con un RETIRO_META sin vincular (SignoMovimiento), desvincula historicos y borra.
  - editarMeta(Long metaId, MetaAhorroCreacionDTO): Modifica propiedades
    respetando las restricciones de la meta por defecto.

* DeudaService (unico productor de PAGO_DEUDA y unico lugar donde se calculan saldos)
  - crearDeuda(DeudaCreacionDTO): Resuelve las condiciones con MotorFinanciero,
    calcula la tabla y persiste montoTotal, valorCuota, tasas y costos.
  - obtenerDeudasPorUsuario(String rut): Lista via proyeccion JPQL y enriquece
    cada DTO en memoria (motor + calendario + ImputacionPagos).
  - registrarPago(Long deudaId, PagoDeudaDTO): valida propiedad y estado
    PENDIENTE; calcula el monto segun modoPago; crea el PAGO_DEUDA (SignoMovimiento),
    asocia categoria "Deudas" y pasa a PAGADA si se cubre el total. Devuelve
    ResultadoPago(deuda, movimiento).
  - editarDeuda(Long deudaId, DeudaCreacionDTO): sin pagos recalcula todas las
    condiciones; con pagos solo nombre/descripcion/tipoDeuda/cuotasPagadasPrevias
    (recalcula montoPagadoPrevio); enviar condiciones/montoTotal/cantidadCuotas -> 409.
  - cancelarDeuda(Long deudaId): Pasa estado a CANCELADA si no esta PAGADA.
  - obtenerAmortizacion(Long deudaId): cronograma con estado/pagado/previa.
  - obtenerDeuda(Long deudaId): ficha enriquecida (valida propiedad -> 403).
  - obtenerPagos(Long deudaId, page, size): historial paginado con desglose en
    memoria (imputacion acumulada menos la anterior), una sola consulta.
  - ResultadoPago (record interno): deuda resultante + movimiento creado.

* PresupuestoService (T5)
  - obtenerConfiguracion / guardarConfiguracion: 50/30/20 (suma exacta 100.00,
    ningun porcentaje negativo) y reemplazo de asignaciones a metas (valida
    propiedad de cada meta).
  - obtenerCategorias / reemplazarCategorias: limites por categoria (valida
    categoria existente, limite > 0 y sin repetidos).
  - obtenerEjecucionCategorias(rut, month, year): gastado vs. limite y estado.
  - calcularEjecucionGeneral(rut, YearMonth): base reutilizable por /ejecucion/me
    y por el historial (no se duplica).
  - obtenerHistorial(rut, desde, hasta): mes a mes, formato YYYY-MM, max 24 meses.

* SimulacionService (T1b, sin persistencia)
  - simularCredito(SimulacionCreditoRequestDTO): resuelve y calcula con el motor,
    arma condiciones normalizadas, resumen educativo, tabla, comparacion de plazos
    (max 5) y advertencias (CAE referencial; sobreendeudamiento si >30% del ingreso).

* CategoriaService
  - obtenerTodas(): Retorna la coleccion de categorias como DTOs.

* Paquete service/finanzas (motor financiero puro, sin BD ni Spring)
  - CalculoFinancieroService: cuota francesa, tabla de amortizacion, CAE y
    conversion de tasas; biseccion para tasas implicitas y CAE con costos.
  - CalendarioCuotas: fechas de vencimiento mensuales (dia ancla) y conteo de cuotas.
  - ResolutorCondiciones: valida y normaliza CondicionesCreditoInput (reglas por
    modalidad en %; SIN_INTERES no admite tasa, TASA_CONOCIDA exige una sola tasa,
    CUOTA_CONOCIDA exige valorCuota > 0 y no admite tasas).
  - ImputacionPagos: clase pura que reparte los pagos cuota a cuota (interes ->
    costo adicional -> capital); expone EstadoCuota, montoProximaCuotaImpaga,
    capitalImputado y contarPagadas. Nada se persiste.
  - MotorFinanciero: fachada de los tres componentes (resolver, calcular,
    fechasVencimiento).
  - CondicionesCredito / ResultadoCalculo / CuotaAmortizacion: records de entrada,
    salida y fila de tabla.
  - CalculoFinancieroException: excepcion de negocio (HTTP 400).

* service/movimiento
  - SignoMovimiento: regla canonica de signo. aplicar(tipo, monto) devuelve el
    monto en valor absoluto con escala 2 (HALF_UP) y lo niega si el tipo es
    GASTO_GENERAL, PAGO_DEUDA o ABONO_META; monto 0/nulo -> IllegalArgumentException.
    esNegativo(tipo) informa el signo. Es la unica clase que llama a negate() sobre

  - FechasMovimiento: unica frontera entre java.time (LocalDate/YearMonth) y
    java.util.Date; zona fijada una sola vez (systemDefault).

* ReporteService & Generadores
  - exportarMovimientos(String rut, String alcance, String formato, Integer mes, Integer anio):
    Filtra movimientos por rango temporal y delega la generacion a la estrategia correspondiente.
  - PdfReporteGenerator: Construye el PDF mediante OpenPDF en formato A4 con tablas 
    estilizadas, alternancia de filas (zebra), colores rojo/verde por monto y metadatos.
  - CsvReporteGenerator: Construye un CSV delimitado por punto y coma (;) inyectando 
    el BOM UTF-8 (0xEF, 0xBB, 0xBF) y escapando caracteres especiales.

8. REGLAS DE NEGOCIO Y FLUJOS DE TRABAJO (MAPAS CONCEPTUALES EN TEXTO)
================================================================================

--------------------------------------------------------------------------------
REGLAS TRANSVERSALES (T1d, T2, T3, T4, T5)
--------------------------------------------------------------------------------

R1. SIGNO CANONICO DE LOS MOVIMIENTOS (T1d)
- El signo lo impone el tipo, no el cliente ni el productor:
    Positivos: INGRESO_GENERAL, RETIRO_META
    Negativos: GASTO_GENERAL, PAGO_DEUDA, ABONO_META
- SignoMovimiento.aplicar(tipo, monto) devuelve el monto en valor absoluto con
  escala 2 (HALF_UP) y lo niega si corresponde. Monto 0 o nulo, o tipo sin signo
  definido -> IllegalArgumentException (HTTP 400).
- Productores obligados a usarlo: MovimientoService.registrarMovimiento,
  DeudaService.registrarPago, MetaAhorroService (abonar, retirar y el reintegro
  al eliminar meta) y SmartSplitProcessor.
- Es la unica clase que llama a negate() sobre montos de movimientos. Saldo =
  SUM(MOVIMIENTO.monto).
- Si se agrega un valor a TipoMovimiento hay que actualizar SignoMovimiento y el
  CHECK de la BD en la misma tarea.
- Red de seguridad en la BD (V4): CHECK chk_movimiento_signo sobre MOVIMIENTO:
    (tipo IN ('INGRESO_GENERAL','RETIRO_META') AND monto > 0)
    OR (tipo IN ('GASTO_GENERAL','PAGO_DEUDA','ABONO_META') AND monto < 0).
  Se creo NOT VALID (el historico podia violarlo y el arranque no falla), pero
  desde ya rechaza INSERT/UPDATE invalidos. El script trae la consulta de
  diagnostico y el VALIDATE comentados; V8 finalmente valida el constraint.

R2. INVARIANTE DE METAS
- Tras abonar, retirar, Smart-Split y eliminar, montoActual de la meta =
  -(suma de movimientos ABONO_META vinculados a esa meta).
- Al eliminar una meta con ahorro se crea un RETIRO_META (positivo) por el total
  ahorrado, SIN vincular a la meta.

R3. IMPUTACION DE PAGOS (T2/T3)
- ImputacionPagos (clase pura, service.finanzas) reparte los pagos reales cuota
  por cuota y, dentro de cada cuota, en este orden: interes -> costo adicional ->
  capital. Las cuotasPagadasPrevias cuentan como completas ya pagadas y los pagos
  reales empiezan en la siguiente. Nada de la imputacion se persiste.
- DeudaService.registrarPago es el UNICO productor de PAGO_DEUDA; POST
  /api/v1/movimientos con ese tipo delega en el. modoPago CUOTA_CALCULADA cobra lo
  que falta de la proxima cuota impaga (cuota + costo adicional);
  MONTO_PERSONALIZADO (por defecto) exige monto > 0. Sobrepago o deuda no
  PENDIENTE -> 409; deuda ajena -> 403.
- Detalle e historial (T3): GET /api/v1/deudas/{id} (ficha con derivados),
  /amortizacion (estado PAGADA|PARCIAL|PENDIENTE, montoPagado, previa) y /pagos
  (paginado fecha desc; desglose = imputacion acumulada tras ese pago menos la
  anterior, en memoria y con una sola consulta). CuotaSimulacionDTO.from(tabla,
  fechas) es el mapper compartido por el simulador y el detalle.
- DeudaResponseDTO calcula en memoria, sobre la proyeccion JPQL y sin consultas
  extra: tasas en porcentaje, valorCuota, fechaUltimaCuota, montoPagado,
  montoRestante/totalPorPagar, saldoCapital, cuotasPagadas, proximaCuota*,
  interesesPagados. Si una deuda no se puede recalcular, sus derivados quedan en
  null y el listado sigue.

R4. HISTORIAL FILTRADO Y EDICION DE MOVIMIENTOS (T4)
- GET /api/v1/movimientos/paginados/me acepta filtros opcionales (desde/hasta ISO
  inclusivos, tipoMovimiento, categoriaId, montoMin/montoMax contra la magnitud
  (valor absoluto) del monto, q case-insensitive con % y _ escapados) via JPA
  Specifications, siempre filtrando por el RUT del token. 400 si desde>hasta,
  montoMin/montoMax negativos o montoMin>montoMax.
- PUT/DELETE /api/v1/movimientos/{id} solo aplican a INGRESO_GENERAL y GASTO_GENERAL
  sin deuda ni meta (el resto -> 409 "se modifica desde su modulo"), exigen
  propiedad (ajeno -> 403) y rechazan con 409 un ingreso con movimientos derivados
  (movimiento_origen_id). La fecha no se edita; el monto se reescribe con
  SignoMovimiento.
- El PUT es parcial: descripcion, monto y categoriaId son opcionales y solo se
  aplican los enviados (no nulos); los omitidos conservan su valor. Los
  movimientos historicos sin vinculo no tienen esa restriccion.
- FechasMovimiento (service.movimiento) es la unica clase que mezcla java.time
  con java.util.Date; la zona se fija una sola vez.

R5. PRESUPUESTO POR CATEGORIA E HISTORIAL (T5)
- PresupuestoService calcula el mes completo en la ventana semiabierta
  [inicioDeMes, inicioDeMesSiguiente) de FechasMovimiento.
- GET/PUT /categorias/me lee/reemplaza el conjunto de limites (PUT valida
  categoria existente, limite > 0 y sin repetidas; si no -> 400), siempre por el
  RUT del token.
- GET /categorias/ejecucion/me: gastado = suma en abs de GASTO_GENERAL y
  PAGO_DEUDA de esa categoria en el mes; estado = EstadoEjecucion.desdePorcentaje
  (UMBRAL_ALERTA=80, UMBRAL_EXCEDIDO=100) -> OK / ALERTA / EXCEDIDO.
- GET /historial/me?desde&hasta (YYYY-MM, inclusivos) reutiliza
  calcularEjecucionGeneral mes a mes; max 24 meses, rango invertido o formato
  invalido -> 400. Un mes sin ingresos devuelve ceros (sin dividir por 0).
- POST /me exige necesidades + deseos + ahorro = 100.00 (compareTo) y ningun
  porcentaje negativo; responde ConfiguracionPresupuestoResponseDTO (no la entidad).

FLUJO 4: METAS DE AHORRO Y ELIMINACION CON REEMBOLSO
--------------------------------------------------------------------------------

Escenario A: Abono a Meta
  [POST /api/v1/metas/{id}/abonar (monto)]
  -> Crea movimiento ABONO_META con monto negativo (-monto) que resta del saldo.
  -> Incrementa meta.montoActual += monto.
  -> Retorna la meta con saldo actualizado.

Escenario B: Retiro de Meta
  [POST /api/v1/metas/{id}/retirar (monto)]
  -> Verifica si monto > totalAhorrado. Si es mayor, rechaza con 409 Conflict.
  -> Crea movimiento RETIRO_META con monto positivo (+monto) que suma al saldo.
  -> Decrementa meta.montoActual -= monto.
  -> Retorna la meta actualizada.

Escenario C: Eliminacion de Meta
  [DELETE /api/v1/metas/{id}]
  -> ¿Es la meta 'Ahorros' por defecto? -> Rechazar con 409 Conflict (Protegida).
  -> ¿Tiene ahorros acumulados (> 0)?
       SI -> Crear movimiento RETIRO_META con descripcion "Devolucion de fondos..."
             para que el dinero retorne integramente al saldo principal del usuario.
  -> Desvincular todos los movimientos historicos (m.setMetaAhorro(null)).
  -> Eliminar el registro de la entidad MetaAhorro de la base de datos.
  -> Retornar 200 OK con mensaje de confirmacion.

10. MIGRACION DE ESQUEMA Y DATOS CON FLYWAY
================================================================================

A partir del commit 1da0dd3 (2026-10-01, "Actualización e implementación de
Flyway"), el proyecto adopta Flyway como sistema de migracion de esquema
versionada. Este cambio reemplaza la creacion de tablas por Hibernate DDL-auto
y el poblado imperativo del DataLoader, introduciendo un ciclo de vida
declarativo, reproducible y auditable para el esquema de la base de datos.

10.1. MOTIVACION Y JUSTIFICACION DEL CAMBIO
--------------------------------------------------------------------------------
Problemas resueltos:
1) Hibernate ddl-auto=update generaba el esquema de forma implicita y no
   dejaba registro versionado de los cambios. Cada despliegue podia alterar
   columnas o constraints sin trazabilidad.
2) El DataLoader (CommandLineRunner) ejecutaba logica Java imperativa para
   poblar categorias. No era reproducible entre entornos y carecia de
   idempotencia robusta en despliegues multi-instancia o rollbacks.
3) El proyecto usa ahora un unico motor de BD: Supabase PostgreSQL. Todos los
   scripts viven en db/migration/postgresql y se aplican igual en dev y prod.

Beneficios obtenidos:
- Versionado explicito: Cada cambio de esquema es un script SQL numerado
  (V1, V2, ...) rastreable en Git.
- Idempotencia: Los scripts usan CREATE TABLE IF NOT EXISTS y
  ON CONFLICT DO NOTHING para ser re-ejecutables.
- Tabla de auditoria: Flyway crea y mantiene la tabla flyway_schema_history
  con checksums, timestamps y estado de cada migracion aplicada.

10.2. DEPENDENCIAS MAVEN (pom.xml)
--------------------------------------------------------------------------------
La version de Flyway se fija de forma explicita con la propiedad
<flyway.version>10.20.0</flyway.version> (sobrescribe la del BOM). Ademas de
flyway-core se declara el modulo de PostgreSQL:

  <properties>
      <java.version>21</java.version>
      <flyway.version>10.20.0</flyway.version>
  </properties>

  <!-- flyway-core: version fijada por la propiedad flyway.version (10.20.0) -->
  <dependency>
      <groupId>org.flywaydb</groupId>
      <artifactId>flyway-core</artifactId>
  </dependency>
  <!-- Requerido en Flyway 10+ para soporte explicito de PostgreSQL -->
  <dependency>
      <groupId>org.flywaydb</groupId>
      <artifactId>flyway-database-postgresql</artifactId>
  </dependency>

Notas:
- flyway-core no declara version en la dependencia; hereda la propiedad
  flyway.version (10.20.0).
- flyway-database-postgresql es obligatorio desde Flyway 10 para el soporte
  explicito de PostgreSQL (antes estaba integrado en flyway-core).
- Las dependencias de Oracle (ucp, ojdbc11, oraclepki, ojdbc11-production) y
  flyway-database-oracle fueron eliminadas: el proyecto ya no se conecta a Oracle.

10.3. CONFIGURACION POR PERFIL (application-*.properties)
--------------------------------------------------------------------------------

10.3.1. Perfil de Desarrollo (application-dev.properties)
  # JPA: Hibernate solo VALIDA que el esquema coincida con las entidades.
  # Flyway es el responsable de crear y evolucionar las tablas.
  spring.jpa.hibernate.ddl-auto=validate

  # Flyway apunta a los scripts PostgreSQL (Supabase)
  spring.flyway.locations=classpath:db/migration/postgresql
  spring.flyway.baseline-on-migrate=true
  spring.flyway.baseline-version=0
  spring.flyway.validate-on-migrate=true

10.3.2. Perfil de Produccion (application-prod.properties)
  # JPA: Hibernate NO toca el esquema en absoluto.
  # Flyway es el unico responsable de crear y migrar.
  spring.jpa.hibernate.ddl-auto=none

  # Flyway apunta a los mismos scripts PostgreSQL
  spring.flyway.locations=classpath:db/migration/postgresql
  spring.flyway.baseline-on-migrate=true
  spring.flyway.baseline-version=0
  spring.flyway.validate-on-migrate=true

Explicacion de propiedades clave:
- spring.flyway.locations: Ruta al classpath con los scripts SQL. Es la misma en
  dev y prod porque el motor es unico (PostgreSQL).
- spring.flyway.baseline-on-migrate=true: Si la BD ya existe (creada previamente
  por Hibernate), Flyway la marca en la version baseline (V0) y aplica las
  migraciones pendientes (V1, V2, ...) de forma incremental. Esto habilita la
  adopcion de Flyway sobre bases de datos pre-existentes sin perder datos.
- spring.flyway.baseline-version=0: La version de referencia es V0, lo que
  significa que V1 sera la primera migracion real aplicada.
- spring.flyway.validate-on-migrate=true: Antes de aplicar migraciones, Flyway
  verifica que los checksums de los scripts ya aplicados no hayan cambiado.
  Protege contra modificaciones accidentales de scripts historicos.

Relacion Hibernate DDL-auto ↔ Flyway:
- DEV:  ddl-auto=validate → Hibernate valida las entidades contra el esquema
        que Flyway creo. Si hay discrepancias, el arranque falla tempranamente
        detectando errores de mapeo antes de que lleguen a produccion.
- PROD: ddl-auto=none → Hibernate no interfiere con el esquema. Flyway tiene
        control exclusivo. Maximo nivel de seguridad para produccion.

10.4. ESTRUCTURA DE SCRIPTS DE MIGRACION
--------------------------------------------------------------------------------
Ubicacion: src/main/resources/db/migration/

  db/migration/
  └── postgresql/                        ← Motor unico: PostgreSQL (Supabase)
      ├── V1__init_schema.sql            (DDL: creacion de las 7 tablas)
      ├── V2__seed_categories.sql        (DML: 10 categorias con ON CONFLICT)
      ├── V3__deuda_condiciones_credito.sql (DEUDA + condiciones de credito)
      ├── V4__movimiento_check_signo.sql (CHECK chk_movimiento_signo, NOT VALID)
      ├── V5__movimiento_origen_id.sql   (movimiento_origen_id + FK + indice)
      ├── V6__presupuesto_categoria.sql  (PRESUPUESTO_CATEGORIA + RLS)
      ├── V7__rename_constraints.sql     (rebautiza constraints de V3-V6)
      └── V8__normalizar_constraints_indices_rls.sql (minusculas, valida CHECK,
          indices faltantes y RLS en las 8 tablas)

Convencion de nombrado Flyway:
  V{version}__{descripcion}.sql
  - V = Migracion versionada (aplicada una sola vez, en orden numerico).
  - {version} = Numero entero secuencial (1, 2, 3, ...).
  - __ = Doble guion bajo (separador obligatorio).
  - {descripcion} = Nombre descriptivo en snake_case.

10.5. DETALLE DE V1__init_schema.sql (CREACION DEL ESQUEMA)
--------------------------------------------------------------------------------
Crea las 7 tablas del modelo de datos de forma idempotente:

Orden de creacion (respeta dependencias de Foreign Keys):
  1. USUARIO           (sin FK, es la raiz del modelo)
  2. CATEGORIA         (sin FK a otras tablas del modelo)
  3. META_AHORRO       (FK → USUARIO)
  4. DEUDA             (FK → USUARIO)
  5. MOVIMIENTO        (FK → USUARIO, DEUDA, CATEGORIA, META_AHORRO)
  6. CONFIGURACION_PRESUPUESTO  (FK → USUARIO, relacion 1:1)
  7. ASIGNACION_META_PRESUPUESTO (FK → CONFIGURACION_PRESUPUESTO, META_AHORRO)

Tipos PostgreSQL usados en el esquema:
  +-----------------------------+---------------------------------------------+
  | Aspecto                     | PostgreSQL (Supabase)                       |
  +-----------------------------+---------------------------------------------+
  | Cadenas de texto            | VARCHAR(n)                                  |
  | Numeros decimales           | NUMERIC(19,2)                               |
  | Enteros                     | INTEGER                                     |
  | Identidad auto-incremental  | BIGINT GENERATED BY DEFAULT AS IDENTITY     |
  | Booleanos                   | BOOLEAN nativo                              |
  | Idempotencia DDL            | CREATE TABLE IF NOT EXISTS                  |
  +-----------------------------+---------------------------------------------+

Constraints implementados:
  - Primary Keys (PK_*): Cada tabla tiene su PK nombrado explicitamente.
  - Unique (UQ_*): USUARIO.email, CATEGORIA.nombre, CONFIGURACION.usuario_id.
  - Foreign Keys (FK_*): Todas las relaciones entre tablas.
  - Check (CHK_*): Validaciones de dominio a nivel de BD:
    * CATEGORIA.tipo_presupuesto IN ('NECESIDAD','DESEO','AHORRO','OTROS')
    * DEUDA.estado IN ('PENDIENTE','PAGADA','CANCELADA')
    * MOVIMIENTO.tipo_movimiento IN ('INGRESO_GENERAL','GASTO_GENERAL',
      'PAGO_DEUDA','ABONO_META','RETIRO_META')
Nota: V1 solo crea 7 tablas. La octava (PRESUPUESTO_CATEGORIA) llega en V6, y
los CHECK de DEUDA.tipo_deuda/modalidad_calculo, el CHECK de signo de MOVIMIENTO
y las restricciones de PRESUPUESTO_CATEGORIA se agregan en V3, V4 y V6; V8 los
normaliza y valida (ver 10.7).

10.8. ELIMINACION DEL DATALOADER LEGACY
--------------------------------------------------------------------------------
Archivo eliminado: com.example.saveup.config.DataLoader (CommandLineRunner)

Historial: la clase poblabo las 10 categorias iniciales y normalizaba el
TipoPresupuesto de categorias existentes mediante un switch/case. Primero se
deshabilito (se comento la anotacion @Component) al adoptar Flyway, y finalmente
se elimino del repositorio porque su logica quedo cubierta por
V2__seed_categories.sql.

Implicaciones:
  - Spring Boot no registra ningun CommandLineRunner de poblado: el metodo run()
    nunca se ejecuta durante el arranque de la aplicacion.
  - La logica de poblado de categorias y normalizacion de TipoPresupuesto queda
    absorbida por V2__seed_categories.sql.
  - Si en el futuro se requiere una migracion de datos compleja (ej.
    normalizacion de registros existentes), se crea un nuevo script Flyway
    (V9, V10, ...); nunca se reactiva un cargador imperativo en Java.

10.10. GUIA PARA FUTURAS MIGRACIONES
--------------------------------------------------------------------------------
Para anadir cambios al esquema o datos semilla:

1. Crear un nuevo script en db/migration/postgresql:
   - src/main/resources/db/migration/postgresql/V{n}__descripcion.sql
   Calcula n mirando el ultimo script existente en esa carpeta.

2. Respetar la numeracion secuencial (V9, V10, ...).

3. NUNCA modificar scripts ya aplicados (V1..V8). Flyway valida checksums
   y rechazara el arranque si detecta alteraciones.

4. Para cambios de esquema:
   - Usar ALTER TABLE para agregar/modificar columnas.
   - Tipos: NUMERIC(19,2) para dinero, INTEGER para enteros, BOOLEAN para flags.
   - Crear indices o constraints adicionales (nombrados PK_*, UQ_*, FK_*, CHK_*).
   - En tablas con filas antiguas, agrega un CHECK con NOT VALID y valídalo
     despues con VALIDATE CONSTRAINT.

5. Para datos semilla adicionales:
   - Usar ON CONFLICT DO NOTHING para que el script sea re-ejecutable.

6. Probar con el perfil dev (Supabase PostgreSQL) antes de desplegar en prod
   (misma base, otra instancia).

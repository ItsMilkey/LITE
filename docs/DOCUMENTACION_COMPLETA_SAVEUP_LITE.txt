1. RESUMEN EJECUTIVO Y OBJETIVOS
================================================================================

SaveUp Lite es una aplicacion backend de servicios REST orientada a la gestion 
financiera personal inteligente. Permite a los usuarios registrar ingresos y 
gastos, organizar sus finanzas bajo la popular regla de presupuesto 50/30/20, 
gestionar metas de ahorro con distribucion automatica (Smart-Split), monitorear 
y amortizar deudas en cuotas con calculos en tiempo real, y generar reportes 
exportables estructurados en PDF y CSV.

Aspectos destacados:
- Modelo financiero integral: ingresos, gastos, deudas, metas y presupuestos 
  conectados sin fisuras de integridad.
- Smart-Split: asignacion automatizada de porcentajes de ahorro a metas al 
  percibir ingresos generales.
- Calculos en tiempo real: saldos de cuenta, montos acumulados por meta, montos 
  pagados y restantes en deudas, y porcentaje de ejecucion presupuestaria.
- Alta compatibilidad de exportacion: PDFs con estilos corporativos listos para 
  impresion y CSVs optimizados con UTF-8 BOM para apertura directa en Excel.
- Despliegue preparado para produccion en contenedores Docker ligeros con 
  mantenimiento activo de disponibilidad mediante GitHub Actions.

2. ARQUITECTURA TECNOLOGICA Y ESTRUCTURA DE CAPAS
================================================================================

El backend sigue una arquitectura clasica por capas (N-Tier Layered Architecture),
combinada con patrones de diseno como Data Transfer Object (DTO) y Strategy:

[Cliente HTTP / Frontend (Ionic, Capacitor, Web)]
                     |
                     v
   [Capa Controladores REST (@RestController)]
     - Recibe peticiones HTTP, valida DTOs de entrada (@Valid).
     - Retorna ResponseEntity con HTTP Status apropiados.
                     |
                     v
     [Capa de Servicios (@Service)]
     - Implementa las reglas de negocio y transacciones (@Transactional).
     - Transforma entidades a DTOs de respuesta para aislar el modelo interno.
     - Aplica el patron Strategy para exportacion de reportes.
                     |
                     v
   [Capa de Repositorios (@Repository / JpaRepository)]
     - Consultas derivadas de Spring Data JPA.
     - Consultas JPQL optimizadas mediante @Query con agregaciones SUM, COUNT.
                     |
                     v
   [Capa de Persistencia / Entidades (@Entity)]
     - Mapeo relacional JPA/Hibernate contra Oracle Autonomous Database.
     - Gestion del ciclo de vida de entidades con @PrePersist.

3. MODELO DE DATOS Y ESQUEMA DE ENTIDADES (JPA / HIBERNATE)
================================================================================

3.1. ENTIDAD USUARIO (Tabla: USUARIO)
--------------------------------------------------------------------------------
Representa al propietario de las cuentas y finanzas.
Campos:
- rut (String, PK, unico): Identificador nacional unico (ej. "12345678-9").
- nombre (String, NOT NULL): Nombre del usuario.
- apellido (String, NOT NULL): Apellido del usuario.
- email (String, NOT NULL, UNIQUE): Direccion de correo electronico.
- contrasena (String, NOT NULL, length=100): Hash BCrypt de la contrasena.
- fechaRegistro (Date, NOT NULL, updatable=false): Fecha y hora de creacion.
Ciclo de vida:
- @PrePersist onCreate(): Si fechaRegistro es nula, inicializa con new Date().

3.2. ENTIDAD CATEGORIA (Tabla: CATEGORIA)
--------------------------------------------------------------------------------
Clasifica los movimientos y los asocia a una regla presupuestaria.
Campos:
- id (Long, PK, Auto-incremental IDENTITY): Identificador de la categoria.
- nombre (String, NOT NULL, UNIQUE): Nombre (ej. "Comida", "Transporte").
- iconId (String): Nombre del icono para la UI (ej. "ic_fastfood", "ic_work").
- colorHex (String): Codigo hexadecimal de color (ej. "#FFC107").
- tipoPresupuesto (Enum TipoPresupuesto): Clasificacion presupuestaria 
  (NECESIDAD, DESEO, AHORRO, OTROS).

3.3. ENTIDAD MOVIMIENTO (Tabla: MOVIMIENTO)
--------------------------------------------------------------------------------
Representa cada transaccion financiera realizada por el usuario.
Campos:
- id (Long, PK, Auto-incremental IDENTITY): Identificador unico de transaccion.
- monto (BigDecimal, NOT NULL): Cantidad monetaria. Positiva para ingresos y retiros 
  de metas; negativa para gastos, pagos de deudas y abonos a metas.
- descripcion (String, NOT NULL, length=100): Detalle descriptivo del movimiento.
- fecha (Date, NOT NULL, updatable=false): Marca de tiempo del movimiento.
- tipoMovimiento (Enum TipoMovimiento, NOT NULL): Naturaleza del movimiento.
- usuario (ManyToOne, NOT NULL, Lazy): Relacion al Usuario dueno del movimiento.
- categoria (ManyToOne, Eager, Nullable): Categoria asignada.
- deuda (ManyToOne, Lazy, Nullable): Deuda vinculada si el tipo es PAGO_DEUDA.
- metaAhorro (ManyToOne, Lazy, Nullable): Meta vinculada si es abono/retiro.
Ciclo de vida:
- @PrePersist onCreate(): Si fecha es nula, inicializa con new Date().

3.4. ENTIDAD META_AHORRO (Tabla: META_AHORRO)
--------------------------------------------------------------------------------
Objetivo de ahorro financiero del usuario.
Campos:
- id (Long, PK, Auto-incremental IDENTITY): Identificador unico de la meta.
- nombre (String, NOT NULL, length=100): Titulo o motivo (ej. "Vacaciones").
- montoObjetivo (BigDecimal, Nullable): Monto final deseado. Es nulo en la meta 
  por defecto "Ahorros".
- montoActual (BigDecimal, Default 0.00): Monto total acumulado en la meta.
- fechaLimite (Date, Nullable): Fecha estimada de cumplimiento.
- usuario (ManyToOne, NOT NULL, Lazy): Propietario de la meta.
Metodo auxiliar:
- getMontoActual(): Retorna montoActual != null ? montoActual : BigDecimal.ZERO.

3.5. ENTIDAD DEUDA (Tabla: DEUDA)
--------------------------------------------------------------------------------
Compromiso financiero o pasivo adquirido por el usuario.
Campos:
- id (Long, PK, Auto-incremental IDENTITY): Identificador de la deuda.
- nombre (String, NOT NULL, length=100): Titulo (ej. "Credito de Consumo").
- descripcion (String, length=255, Nullable): Informacion adicional.
- montoTotal (BigDecimal, NOT NULL): Monto global comprometido a pagar.
- cantidadCuotas (int, NOT NULL): Total de cuotas pactadas.
- estado (Enum EstadoDeuda, NOT NULL): PENDIENTE, PAGADA o CANCELADA.
- fechaCreacion (Date, NOT NULL, updatable=false): Fecha de ingreso de la deuda.
- usuario (ManyToOne, NOT NULL, Lazy): Usuario deudor.
Ciclo de vida:
- @PrePersist onCreate(): Establece fecha actual y estado PENDIENTE por defecto.

3.6. ENTIDAD CONFIGURACION_PRESUPUESTO (Tabla: CONFIGURACION_PRESUPUESTO)
--------------------------------------------------------------------------------
Configuracion del esquema de distribucion de ingresos del usuario (regla 50/30/20).
El presupuesto actua como guia de control y visualizacion de gastos (Necesidades /
Deseos / Ahorro); la ejecucion fisica de abonos automaticos a metas es opcional.
Campos:
- id (Long, PK, Auto-incremental IDENTITY): Identificador de la configuracion.
- usuario (OneToOne, NOT NULL): Usuario asociado (relacion 1 a 1).
- porcentajeNecesidades (BigDecimal, NOT NULL): Porcentaje asignado (ej. 50.00).
- porcentajeDeseos (BigDecimal, NOT NULL): Porcentaje asignado (ej. 30.00).
- porcentajeAhorro (BigDecimal, NOT NULL): Porcentaje asignado (ej. 20.00).
- activo (Boolean, NOT NULL, default=true): Indica si la configuracion esta habilitada.
- automatizarAhorroEnMetas (Boolean, NOT NULL, default=false): Bandera de desacoplamiento.
  * false (por defecto): El presupuesto actua solo como guia visual 50/30/20. El dinero
    permanece 100% liquido en el saldo principal; no se generan sub-movimientos ABONO_META.
  * true: Smart-Split ejecuta la distribucion fisica del porcentaje de ahorro hacia las
    metas configuradas, creando movimientos ABONO_META y debitando el saldo principal.
Ciclo de vida (@PrePersist / @PreUpdate):
- Si activo es null, se inicializa en true.
- Si automatizarAhorroEnMetas es null, se inicializa en false (seguridad defensiva).

3.7. ENTIDAD ASIGNACION_META_PRESUPUESTO (Tabla: ASIGNACION_META_PRESUPUESTO)
--------------------------------------------------------------------------------
Sub-distribucion del porcentaje de ahorro hacia metas individuales especificas.
Campos:
- id (Long, PK, Auto-incremental IDENTITY): Identificador de la asignacion.
- configuracion (ManyToOne, NOT NULL, Lazy): Configuracion a la que pertenece.
- meta (ManyToOne, NOT NULL, Eager): Meta de ahorro beneficiaria.
- porcentajeAsignacion (BigDecimal, NOT NULL): Fraccion del ahorro total (ej. 60.00%).

4. CATALOGO COMPLETO DE ENUMS
================================================================================

4.1. Enum: TipoMovimiento
-------------------------
Ubicacion: com.example.saveup.model.enums.TipoMovimiento
Valores:
- INGRESO_GENERAL : Entrada de dinero principal (sueldos, rentas, transferencias).
                    Puede disparar el algoritmo Smart-Split si asi se indica.
- GASTO_GENERAL   : Salida ordinaria de dinero (alimentacion, ocio, cuentas).
- PAGO_DEUDA      : Amortizacion de una cuota o monto de una deuda existente.
- ABONO_META      : Traslado de dinero desde el saldo principal hacia una meta.
- RETIRO_META     : Rescate de dinero desde una meta hacia el saldo principal.

4.2. Enum: EstadoDeuda
----------------------
Ubicacion: com.example.saveup.model.enums.EstadoDeuda
Valores:
- PENDIENTE : La deuda esta vigente y admite abonos/pagos de cuotas.
- PAGADA    : El total pagado ha igualado o superado el montoTotal.
- CANCELADA : La deuda fue dada de baja de forma manual por el usuario.

4.3. Enum: TipoPresupuesto
--------------------------
Ubicacion: com.example.saveup.model.enums.TipoPresupuesto
Valores:
- NECESIDAD : Gastos vitales imprescindibles (supermercado, arriendo, luz, salud).
              Base del 50% de la regla presupuestaria.
- DESEO     : Gastos de ocio, placer y estilo de vida (cine, salidas, ropa, viajes).
              Base del 30% de la regla presupuestaria.
- AHORRO    : Categorias que representan acumulacion de capital o inversiones.
              Base del 20% de la regla presupuestaria.
- OTROS     : Entradas u otros conceptos que no clasifican como gasto 
              presupuestario estandar.

5.12. ConfiguracionPresupuestoRequestDTO
- Proposito: Establecer o modificar los parametros del presupuesto 50/30/20 y la
  opcion de automatizacion de abonos a metas.
- Campos y Validaciones:
  * porcentajeNecesidades (Double): @NotNull, @DecimalMin("0.0"), @DecimalMax("100.0")
  * porcentajeDeseos (Double): @NotNull, @DecimalMin("0.0"), @DecimalMax("100.0")
  * porcentajeAhorro (Double): @NotNull, @DecimalMin("0.0"), @DecimalMax("100.0")
  * activo (Boolean): Opcional, default true.
  * automatizarAhorroEnMetas (Boolean): Opcional, default false.
    - false: El presupuesto funciona como guia visual; ningun ABONO_META se genera.
    - true: Smart-Split ejecutara distribucion fisica al registrar un INGRESO_GENERAL
            con aplicarPresupuesto=true.
  * asignaciones (List<AsignacionPresupuestoDTO>): @Valid. Lista de sub-distribuciones
    del porcentaje de ahorro hacia metas individuales. Requerido solo si
    automatizarAhorroEnMetas=true y se desea distribucion granular por meta.

5.13. AsignacionPresupuestoDTO
- Proposito: Declarar que fraccion del ahorro se destinara a una meta concreta.
- Campos y Validaciones:
  * metaId (Long): @NotNull. ID de la meta de ahorro beneficiaria.
  * porcentaje (Double): @NotNull, @DecimalMin("0.0"), @DecimalMax("100.0").
    Fraccion del monto total de ahorro a derivar (ej. 60.0 -> 60% del ahorro va a esa meta).

5.14. EjecucionPresupuestoDTO
- Proposito: Comparativa mensual de presupuesto proyectado vs ejecucion real,
  incluyendo metricas de ahorro y el estado de automatizacion configurado.
- Campos:
  * presupuestoNecesidades (Double)     : (Total Ingresos * % Necesidades)
  * gastoNecesidades (Double)           : Suma real de gastos clasificados como NECESIDAD
  * presupuestoDeseos (Double)          : (Total Ingresos * % Deseos)
  * gastoDeseos (Double)                : Suma real de gastos clasificados como DESEO
  * presupuestoAhorro (Double)          : (Total Ingresos * % Ahorro) — monto objetivo
  * ahorroRealizado (Double)            : Suma de egresos ABONO_META del mes (ahorro fisico
                                          efectivamente movido a metas via Smart-Split o manual)
  * totalIngresos (Double)              : Total acumulado de INGRESO_GENERAL del mes
  * porcentajeNecesidadesConfigurado (Double): % configurado para Necesidades
  * porcentajeDeseosConfigurado (Double)     : % configurado para Deseos
  * porcentajeAhorroConfigurado (Double)     : % configurado para Ahorro
  * automatizarAhorroEnMetas (Boolean)       : Refleja si la automatizacion fisica
                                               de abonos a metas esta habilitada.

5.15. PageResponseDTO<T>
- Proposito: Contenedor generico estandarizado para respuestas con paginacion.
- Campos:
  * content (List<T>)
  * currentPage (int)
  * totalItems (long)
  * totalPages (int)

6. MAPA COMPLETO DE ENDPOINTS REST
================================================================================

--------------------------------------------------------------------------------
MODULO: USUARIOS (/api/usuarios)
--------------------------------------------------------------------------------
1. POST /api/usuarios/register (PÚBLICO)
   - Descripcion: Registra un usuario y le crea su meta por defecto "Ahorros".
   - Body: UsuarioRegistroDTO (JSON)
   - Respuestas:
     * 201 Created: {"message": "Usuario registrado exitosamente"}
     * 409 Conflict: {"error": "El RUT ingresado ya está registrado."} o Correo
     * 500 Internal Server Error: {"error": "..."}

2. POST /api/usuarios/login (PÚBLICO)
   - Descripcion: Autentica credenciales mediante BCrypt y retorna el token JWT firmado.
   - Body: UsuarioLoginDTO (JSON)
   - Respuestas:
     * 200 OK: {"token": "eyJhbGci..."}
     * 401 Unauthorized: {"error": "Credenciales inválidas."}

3. GET /api/usuarios/me (PROTEGIDO)
   - Descripcion: Obtiene el perfil completo del usuario autenticado (sin contraseña).
   - Cabecera: Authorization: Bearer <token>
   - Respuestas:
     * 200 OK: Entidad Usuario (con contrasena null)
     * 401 Unauthorized / 403 Forbidden

MODULO: SALDOS (/api/saldos)
--------------------------------------------------------------------------------
4. GET /api/saldos/me (PROTEGIDO - Implicit Context)
   - Descripcion: Retorna el saldo neto acumulado del usuario autenticado.
   - Cabecera: Authorization: Bearer <token>
   - Respuestas:

7.1. CAPA DE SERVICIOS (Lógica de Negocio)
--------------------------------------------------------------------------------
* UsuarioService
  - registrarUsuario(UsuarioRegistroDTO): Valida duplicidad, aplica BCrypt, 
    persiste al usuario y crea la meta base "Ahorros" de forma transaccional.
  - autenticarUsuario(UsuarioLoginDTO): Verifica contrasena con BCrypt y 
    arroja BadCredentialsException ante fallos.

* MovimientoService
  - registrarMovimiento(MovimientoRegistroDTO): Valida usuario desde SecurityContext, asocia categorias 
    y deudas, y delega la distribucion automatica Smart-Split a SmartSplitProcessor.
  - obtenerMovimientosPorUsuario(String rut, Integer limit): Consulta movimientos 
    ordenados con soporte de limite.
  - obtenerSaldoActual(String rut): Ejecuta la agregacion de saldo neto.
  - obtenerMovimientosPaginados(String rut, Pageable): Retorna envoltorio 
    PageResponseDTO con contenido y metadatos.

* SmartSplitProcessor (com.example.saveup.service.SmartSplitProcessor)
  - procesarDistribucion(Usuario usuario, double montoIngreso): Servicio de dominio
    especializado que desacopla la logica del algoritmo Smart-Split de MovimientoService.
    Implementa el modelo de automatizacion opcional de metas:
    * Condicion de ejecucion (triple AND): config.activo == true
      AND config.automatizarAhorroEnMetas == true
      AND config.porcentajeAhorro > 0.
    * Si la condicion se cumple: Calcula montoAhorro = ingreso * (%ahorro / 100),
      itera sobre asignaciones de metas, genera un Movimiento ABONO_META por cada
      meta (monto negativo, categoria 'Ahorro'), y actualiza meta.montoActual.
    * Si la condicion NO se cumple (automatizarAhorroEnMetas=false o config inactiva):
      No se genera ningun sub-movimiento ni debito adicional. El 100% del ingreso
      permanece liquido en el saldo principal del usuario. El presupuesto actua
      exclusivamente como guia visual de control (50/30/20) sin efectos contables.

* MetaAhorroService
  - crearMeta(MetaAhorroCreacionDTO): Inicializa una meta de ahorro.
  - obtenerMetasPorUsuario(String rut): Lista de metas con saldos.
  - realizarAbono(Long metaId, AbonoRetiroDTO): Descuenta saldo general y 
    abona a meta con categoria "Ahorro".
  - realizarRetiro(Long metaId, AbonoRetiroDTO): Valida fondos suficientes, 
    descuenta de la meta y reintegra al saldo principal.
  - eliminarMeta(Long metaId): Protege la meta por defecto, transfiere fondos 
    al saldo principal si habia ahorro acumulado, desvincula historicos y borra.
  - editarMeta(Long metaId, MetaAhorroCreacionDTO): Modifica propiedades 
    respetando las restricciones de la meta por defecto.

* DeudaService
  - crearDeuda(DeudaCreacionDTO): Registra deuda pendiente.
  - obtenerDeudasPorUsuario(String rut): Lista deudas con campos calculados.
  - registrarPago(Long deudaId, PagoDeudaDTO): Crea movimiento PAGO_DEUDA, 
    asocia categoria "Deudas" y pasa a PAGADA si se cubre el total.
  - editarDeuda(Long deudaId, DeudaCreacionDTO): Permite edicion solo si 
    cuotasPagadas == 0.
  - cancelarDeuda(Long deudaId): Pasa estado a CANCELADA si no esta PAGADA.

* CategoriaService
  - obtenerTodas(): Retorna la coleccion de categorias como DTOs.

* ReporteService & Generadores
  - exportarMovimientos(String rut, String alcance, String formato, Integer mes, Integer anio):
    Filtra movimientos por rango temporal y delega la generacion a la estrategia correspondiente.
  - PdfReporteGenerator: Construye el PDF mediante OpenPDF en formato A4 con tablas 
    estilizadas, alternancia de filas (zebra), colores rojo/verde por monto y metadatos.
  - CsvReporteGenerator: Construye un CSV delimitado por punto y coma (;) inyectando 
    el BOM UTF-8 (0xEF, 0xBB, 0xBF) y escapando caracteres especiales.

FLUJO 4: METAS DE AHORRO Y ELIMINACION CON REEMBOLSO
--------------------------------------------------------------------------------

Escenario A: Abono a Meta
  [POST /api/metas/{id}/abonar (monto)]
  -> Crea movimiento ABONO_META con monto negativo (-monto) que resta del saldo.
  -> Incrementa meta.montoActual += monto.
  -> Retorna la meta con saldo actualizado.

Escenario B: Retiro de Meta
  [POST /api/metas/{id}/retirar (monto)]
  -> Verifica si monto > totalAhorrado. Si es mayor, rechaza con 409 Conflict.
  -> Crea movimiento RETIRO_META con monto positivo (+monto) que suma al saldo.
  -> Decrementa meta.montoActual -= monto.
  -> Retorna la meta actualizada.

Escenario C: Eliminacion de Meta
  [DELETE /api/metas/{id}]
  -> ¿Es la meta 'Ahorros' por defecto? -> Rechazar con 409 Conflict (Protegida).
  -> ¿Tiene ahorros acumulados (> 0)?
       SI -> Crear movimiento RETIRO_META con descripcion "Devolucion de fondos..."
             para que el dinero retorne integramente al saldo principal del usuario.
  -> Desvincular todos los movimientos historicos (m.setMetaAhorro(null)).
  -> Eliminar el registro de la entidad MetaAhorro de la base de datos.
  -> Retornar 200 OK con mensaje de confirmacion.

9.2. POBLADO Y MIGRACION DE DATOS (DataLoader) — LEGACY / DESHABILITADO
- Clase: com.example.saveup.config.DataLoader (CommandLineRunner)
- Estado actual: DESHABILITADO. La anotacion @Component fue comentada en el
  commit 1da0dd3 (2026-10-01) al implementar Flyway como reemplazo definitivo.
- Motivo de deshabilitacion: Flyway gestiona ahora tanto la creacion del esquema
  (V1__init_schema.sql) como la poblacion inicial de categorias (V2__seed_categories.sql)
  de forma versionada, reproducible e idempotente. El DataLoader imperativo queda
  obsoleto porque:
  1) No ofrece versionado de cambios (no hay historial de migraciones).
  2) Depende de logica Java en tiempo de ejecucion, no de scripts SQL declarativos.
  3) No garantiza idempotencia robusta en despliegues multi-instancia.
- El archivo se conserva como referencia historica. Contenia:
  * Poblado condicional de 10 categorias iniciales con iconos, colores y tipo.
  * Normalizacion de categorias existentes sin TipoPresupuesto via switch/case.
  * Garantia de existencia de la categoria "Ahorro".
- Toda esta logica fue portada a los scripts Flyway V2 correspondientes.

10. MIGRACION DE ESQUEMA Y DATOS CON FLYWAY
================================================================================

A partir del commit 1da0dd3 (2026-10-01, "Actualización e implementación de
Flyway"), el proyecto adopta Flyway como sistema de migracion de esquema
versionada. Este cambio reemplaza la creacion de tablas por Hibernate DDL-auto
y el poblado imperativo del DataLoader, introduciendo un ciclo de vida
declarativo, reproducible y auditable para el esquema de la base de datos.

10.1. MOTIVACION Y JUSTIFICACION DEL CAMBIO
--------------------------------------------------------------------------------
Problemas resueltos:
1) Hibernate ddl-auto=update generaba el esquema de forma implicita y no
   dejaba registro versionado de los cambios. Cada despliegue podia alterar
   columnas o constraints sin trazabilidad.
2) El DataLoader (CommandLineRunner) ejecutaba logica Java imperativa para
   poblar categorias. No era reproducible entre entornos y carecia de
   idempotencia robusta en despliegues multi-instancia o rollbacks.
3) El proyecto opera con dos motores de BD diferentes (Oracle en dev,
   PostgreSQL en prod). Mantener scripts SQL separados y versionados por
   dialecto es esencial para la portabilidad.

Beneficios obtenidos:
- Versionado explicito: Cada cambio de esquema es un script SQL numerado
  (V1, V2, ...) rastreable en Git.
- Idempotencia: Los scripts usan CREATE TABLE IF NOT EXISTS, MERGE INTO
  (Oracle) y ON CONFLICT DO NOTHING (PostgreSQL) para ser re-ejecutables.
- Separacion de dialectos: Carpetas independientes por motor, seleccionadas
  automaticamente segun el perfil activo de Spring Boot.
- Tabla de auditoria: Flyway crea y mantiene la tabla flyway_schema_history
  con checksums, timestamps y estado de cada migracion aplicada.

10.2. DEPENDENCIAS MAVEN (pom.xml)
--------------------------------------------------------------------------------
Se anadieron dos dependencias en el bloque de Flyway:

  <!-- flyway-core: version gestionada por el BOM de Spring Boot 3.3 (Flyway 10.x) -->
  <dependency>
      <groupId>org.flywaydb</groupId>
      <artifactId>flyway-core</artifactId>
  </dependency>
  <!-- Requerido en Flyway 10+ para soporte explicito de Oracle -->
  <dependency>
      <groupId>org.flywaydb</groupId>
      <artifactId>flyway-database-oracle</artifactId>
  </dependency>

Notas:
- flyway-core no declara version explicita; hereda la version 10.x del BOM
  de spring-boot-starter-parent 3.3.0.
- flyway-database-oracle es obligatorio desde Flyway 10 para el soporte de
  Oracle (antes estaba integrado en flyway-core).
- Para PostgreSQL no se requiere modulo adicional; el soporte viene incluido
  en flyway-core.

10.3. CONFIGURACION POR PERFIL (application-*.properties)
--------------------------------------------------------------------------------

10.3.1. Perfil de Desarrollo (application-dev.properties)
  # JPA: Hibernate solo VALIDA que el esquema coincida con las entidades.
  # Flyway es el responsable de crear y evolucionar las tablas.
  spring.jpa.hibernate.ddl-auto=validate

  # Flyway apunta a scripts Oracle
  spring.flyway.locations=classpath:db/migration/oracle
  spring.flyway.baseline-on-migrate=true
  spring.flyway.baseline-version=0
  spring.flyway.validate-on-migrate=true

10.3.2. Perfil de Produccion (application-prod.properties)
  # JPA: Hibernate NO toca el esquema en absoluto.
  # Flyway es el unico responsable de crear y migrar.
  spring.jpa.hibernate.ddl-auto=none

  # Flyway apunta a scripts PostgreSQL
  spring.flyway.locations=classpath:db/migration/postgresql
  spring.flyway.baseline-on-migrate=true
  spring.flyway.baseline-version=0
  spring.flyway.validate-on-migrate=true

Explicacion de propiedades clave:
- spring.flyway.locations: Ruta al classpath con los scripts SQL del dialecto
  correspondiente. Permite que los mismos scripts V1, V2, etc. tengan sintaxis
  nativa para cada motor sin colisiones.
- spring.flyway.baseline-on-migrate=true: Si la BD ya existe (creada previamente
  por Hibernate), Flyway la marca en la version baseline (V0) y aplica las
  migraciones pendientes (V1, V2, ...) de forma incremental. Esto habilita la
  adopcion de Flyway sobre bases de datos pre-existentes sin perder datos.
- spring.flyway.baseline-version=0: La version de referencia es V0, lo que
  significa que V1 sera la primera migracion real aplicada.
- spring.flyway.validate-on-migrate=true: Antes de aplicar migraciones, Flyway
  verifica que los checksums de los scripts ya aplicados no hayan cambiado.
  Protege contra modificaciones accidentales de scripts historicos.

Relacion Hibernate DDL-auto ↔ Flyway:
- DEV:  ddl-auto=validate → Hibernate valida las entidades contra el esquema
        que Flyway creo. Si hay discrepancias, el arranque falla tempranamente
        detectando errores de mapeo antes de que lleguen a produccion.
- PROD: ddl-auto=none → Hibernate no interfiere con el esquema. Flyway tiene
        control exclusivo. Maximo nivel de seguridad para produccion.

10.4. ESTRUCTURA DE SCRIPTS DE MIGRACION
--------------------------------------------------------------------------------
Ubicacion: src/main/resources/db/migration/

  db/migration/
  ├── oracle/                            ← Dialecto Oracle 23c (perfil dev)
  │   ├── V1__init_schema.sql            (DDL: creacion de las 7 tablas)
  │   └── V2__seed_categories.sql        (DML: 10 categorias con MERGE INTO)
  └── postgresql/                        ← Dialecto PostgreSQL (perfil prod)
      ├── V1__init_schema.sql            (DDL: creacion de las 7 tablas)
      └── V2__seed_categories.sql        (DML: 10 categorias con ON CONFLICT)

Convencion de nombrado Flyway:
  V{version}__{descripcion}.sql
  - V = Migracion versionada (aplicada una sola vez, en orden numerico).
  - {version} = Numero entero secuencial (1, 2, 3, ...).
  - __ = Doble guion bajo (separador obligatorio).
  - {descripcion} = Nombre descriptivo en snake_case.

10.5. DETALLE DE V1__init_schema.sql (CREACION DEL ESQUEMA)
--------------------------------------------------------------------------------
Crea las 7 tablas del modelo de datos de forma idempotente:

Orden de creacion (respeta dependencias de Foreign Keys):
  1. USUARIO           (sin FK, es la raiz del modelo)
  2. CATEGORIA         (sin FK a otras tablas del modelo)
  3. META_AHORRO       (FK → USUARIO)
  4. DEUDA             (FK → USUARIO)
  5. MOVIMIENTO        (FK → USUARIO, DEUDA, CATEGORIA, META_AHORRO)
  6. CONFIGURACION_PRESUPUESTO  (FK → USUARIO, relacion 1:1)
  7. ASIGNACION_META_PRESUPUESTO (FK → CONFIGURACION_PRESUPUESTO, META_AHORRO)

Diferencias de dialectos entre scripts:
  +-----------------------------+-----------------------+-------------------------+
  | Aspecto                     | Oracle 23c            | PostgreSQL              |
  +-----------------------------+-----------------------+-------------------------+
  | Cadenas de texto            | VARCHAR2(n)           | VARCHAR(n)              |
  | Numeros decimales           | NUMBER(19,2)          | NUMERIC(19,2)           |
  | Enteros                     | NUMBER(10,0)          | INTEGER                 |
  | Identidad auto-incremental  | NUMBER GEN BY DEF     | BIGINT GEN BY DEF       |
  |                             | AS IDENTITY           | AS IDENTITY             |
  | Booleanos                   | NUMBER(1) con 0/1     | BOOLEAN nativo          |
  | Idempotencia DDL            | CREATE TABLE IF NOT   | CREATE TABLE IF NOT     |
  |                             | EXISTS (Oracle 23c+)  | EXISTS (PG 9.1+)        |
  +-----------------------------+-----------------------+-------------------------+

Constraints implementados en ambos dialectos:
  - Primary Keys (PK_*): Cada tabla tiene su PK nombrado explicitamente.
  - Unique (UQ_*): USUARIO.email, CATEGORIA.nombre, CONFIGURACION.usuario_id.
  - Foreign Keys (FK_*): Todas las relaciones entre tablas.
  - Check (CHK_*): Validaciones de dominio a nivel de BD:
    * CATEGORIA.tipo_presupuesto IN ('NECESIDAD','DESEO','AHORRO','OTROS')
    * DEUDA.estado IN ('PENDIENTE','PAGADA','CANCELADA')
    * MOVIMIENTO.tipo_movimiento IN ('INGRESO_GENERAL','GASTO_GENERAL',
      'PAGO_DEUDA','ABONO_META','RETIRO_META')

  |10 | Otro                   | ic_label             | #607D8B | OTROS       |
  +---+------------------------+----------------------+---------+-------------+

Estrategia de idempotencia por dialecto:
  - Oracle 23c: Usa MERGE INTO ... USING (SELECT ... FROM DUAL) ON (nombre)
    WHEN NOT MATCHED THEN INSERT. Este patron DML estandar Oracle evalua la
    condicion de match sobre la restriccion UNIQUE del nombre y solo inserta
    si el registro no existe.
  - PostgreSQL: Usa INSERT INTO ... VALUES (...) ON CONFLICT (nombre) DO NOTHING.
    Aprovecha la clausula nativa de PostgreSQL para inserciones condicionales
    sin duplicados.

10.7. DESHABILITACION DEL DATALOADER LEGACY
--------------------------------------------------------------------------------
Archivo: com.example.saveup.config.DataLoader
Cambio realizado: La anotacion @Component fue comentada:

  // @Component // Deshabilitado: Flyway ahora gestiona el esquema y la
  //               poblacion inicial de datos.
  public class DataLoader implements CommandLineRunner { ... }

Implicaciones:
  - Spring Boot ya no registra DataLoader como bean. El metodo run() nunca se
    ejecuta durante el arranque de la aplicacion.
  - La logica de poblado de categorias y normalizacion de TipoPresupuesto fue
    absorbida por V2__seed_categories.sql.
  - El archivo se conserva en el repositorio como referencia historica y para
    facilitar la comprension de la logica de normalizacion original que incluia
    un switch/case para mapear nombres de categorias a tipos de presupuesto.
  - En caso de requerir migraciones de datos complejas en el futuro (ej.
    normalizacion de registros existentes), se deben crear nuevos scripts
    Flyway V3, V4, etc. en lugar de reactivar el DataLoader.

10.9. GUIA PARA FUTURAS MIGRACIONES
--------------------------------------------------------------------------------
Para anadir cambios al esquema o datos semilla:

1. Crear un nuevo script en AMBAS carpetas de dialecto:
   - src/main/resources/db/migration/oracle/V3__descripcion.sql
   - src/main/resources/db/migration/postgresql/V3__descripcion.sql

2. Respetar la numeracion secuencial (V3, V4, V5, ...).

3. NUNCA modificar scripts ya aplicados (V1, V2). Flyway valida checksums
   y rechazara el arranque si detecta alteraciones.

4. Para cambios de esquema:
   - Usar ALTER TABLE para agregar/modificar columnas.
   - Crear indices o constraints adicionales.

5. Para datos semilla adicionales:
   - Usar las mismas estrategias idempotentes (MERGE INTO / ON CONFLICT).

6. Probar en el perfil dev (Oracle) antes de desplegar en prod (PostgreSQL).

# T9.6 — Recordatorios de vencimiento con notificaciones push

Estado: **implementado en código; PENDIENTE de activación (requiere proveedor externo)** (oct 2026).
Decisiones de §9 aprobadas: FCM, ventanas T-3/T-0/T+1, agrupación por usuario. La bandera maestra
`app.push.enabled` está en `false` por defecto: `RecordatorioService.ejecutar(...)` es no-op total
(no envía y NO persiste `RECORDATORIO_ENVIADO`, para no perder avisos al activar); el registro y la
baja de tokens de dispositivo siguen funcionando. **Qué falta para activar** (`APP_PUSH_ENABLED=true`):
- Proyecto Firebase y credenciales: `FIREBASE_CREDENTIALS` (JSON del service account, en base64) y
  `app.push.log-only=false`.
- La app móvil instalando FCM y registrando su token en `POST /api/v1/notificaciones/dispositivos`
  (con permiso de notificaciones); hoy no hay cliente que registre tokens.
- El disparador externo: cron (Render Cron Job o cron-job.org) contra
  `POST /api/v1/notificaciones/recordatorios/ejecutar` con `X-Cron-Secret` (`PUSH_CRON_SECRET`);
  en Render free el `@Scheduled` interno no es confiable. No hay workflow de GitHub Actions
  programado: el disparador es exclusivamente manual/externo.

Origen: `docs/tareas/T9-sesion-movil.md` (punto "Recordatorios de vencimiento de cuotas").
Depende de: T9.1 (sesión), T9.2 (borrado en cascada), T1a/T3 (calendario de cuotas y próxima cuota impaga).

## 1. Objetivo

Avisar al usuario, sin abrir la app, que una cuota de una de sus deudas está por vencer o
venció. Es la única feature de push del MVP: no hay notificaciones de marketing, de metas ni
de presupuesto en esta tarea.

**Fuera de alcance** (queda en `BACKLOG.md`):

- Alertas de presupuesto (80 % / excedido) y de metas cumplidas.
- Push transaccional de seguridad ("nuevo inicio de sesión").
- Preferencias por tipo de aviso o *quiet hours* configurables por el usuario.
- Entrega garantizada / reintentos con backoff (FCM ya reintenta; no construimos cola propia).

## 2. Decisiones de producto (recomendadas)

| # | Decisión | Recomendación |
|---|---|---|
| D1 | Proveedor | **FCM para Android e iOS** (`firebase-admin`). Un solo SDK y un solo formato; FCM reenvía a APNs. Evita mantener dos integraciones y una llave `.p8` extra. |
| D2 | Cuándo avisar | **T-3 días** (`PROXIMA_VENCER`), **T-0** (`VENCE_HOY`) y **T+1** (`VENCIDA`). `diasAntes` configurable en `app.push.dias-antes=3`. |
| D3 | Agrupación | **Una notificación por usuario y por corrida**, no una por deuda. Si hay 3 cuotas, el cuerpo dice "Tienes 3 cuotas por vencer" y el *tap* abre la lista de deudas. Menos ruido y menos riesgo de que el usuario desactive el permiso. |
| D4 | Hora de envío | **09:00 America/Santiago**, zona de negocio ya fijada en `FechasMovimiento`. No se envía nada entre 22:00 y 08:00. |
| D5 | Consentimiento | El permiso del sistema operativo es la fuente de verdad. El backend solo conoce dispositivos `activo=true`; no se guarda un flag de consentimiento aparte. |
| D6 | Deduplicación | Clave única `(deuda_id, cuota_numero, tipo)` en `RECORDATORIO_ENVIADO`. Si el job corre dos veces el mismo día (reintento de Render, trigger manual), no se duplica. |
| D7 | Credenciales | `FIREBASE_CREDENTIALS` (JSON en base64 en la variable de entorno). Sin credenciales, `app.push.log-only=true` loguea el envío y no falla (igual que `CorreoService`). |

## 3. Modelo de datos (migración `V12__notificaciones_push.sql`)

```
DISPOSITIVO_PUSH(
  id BIGINT PK,
  usuario_id VARCHAR(255) NOT NULL FK → usuario(id_usuario) ON DELETE CASCADE,
  token VARCHAR(255) NOT NULL UNIQUE,      -- token FCM; nunca se loguea completo
  plataforma VARCHAR(10) NOT NULL,          -- ANDROID | IOS
  activo BOOLEAN NOT NULL DEFAULT TRUE,
  fecha_registro TIMESTAMP NOT NULL,
  fecha_ultimo_uso TIMESTAMP NOT NULL
)

RECORDATORIO_ENVIADO(
  id BIGINT PK,
  usuario_id VARCHAR(255) NOT NULL FK → usuario(id_usuario) ON DELETE CASCADE,
  deuda_id BIGINT NOT NULL FK → deuda(id_deuda) ON DELETE CASCADE,
  cuota_numero INT NOT NULL,
  tipo VARCHAR(20) NOT NULL,                -- PROXIMA_VENCER | VENCE_HOY | VENCIDA
  fecha_envio TIMESTAMP NOT NULL,
  CONSTRAINT uq_recordatorio UNIQUE (deuda_id, cuota_numero, tipo)
)
```

Reglas del esquema: RLS habilitado en ambas tablas (regla de V8), índices por `usuario_id`,
FK con `ON DELETE CASCADE` (T9.2). El `UNIQUE(token)` es **global**: un mismo teléfono puede
cambiar de cuenta. Al registrar un token que ya existe con otro `usuario_id`, se reasigna al
usuario actual y se reactiva (nunca se crea un duplicado).

Entidades nuevas: `model/DispositivoPush`, `model/RecordatorioEnviado`.
Enums: `model/enums/Plataforma` (**ya existe**, T9.4) y `model/enums/TipoRecordatorio`.

## 4. API (`/api/v1/notificaciones`)

Todos los endpoints de dispositivos requieren JWT; el usuario sale del token, nunca del cuerpo
(`SecurityUtils`), igual que el resto de `/me`. La única excepción es el trigger de cron, que
autentica con `X-Cron-Secret`.

| Método | Ruta | Cuerpo / Query | Respuesta |
|---|---|---|---|
| POST | `/dispositivos` | `{ "token": "...", "plataforma": "ANDROID\|IOS" }` | `201` `DispositivoPushResponseDTO` · `200` si ya existía activo |
| DELETE | `/dispositivos` | `{ "token": "..." }` | `204` (idempotente: token desconocido → `204`) |
| GET | `/dispositivos` | — | `200` lista (sin exponer el token completo: `tokenEnmascarado`) |
| POST | `/recordatorios/ejecutar` | header `X-Cron-Secret` | `202` `{ evaluados, enviados, omitidos }` |

Detalles:

- `POST /dispositivos` es un *upsert*: token nuevo → crea; token propio existente → actualiza
  `fecha_ultimo_uso` y `activo=true`; token de otro usuario → reasigna.
- `DELETE /dispositivos` se llama en el logout del dispositivo. El logout de T9.1 revoca el
  refresh token; este borrado es adicional y opcional (si falta, el token queda huérfano pero
  el job lo desactiva en el primer `UNREGISTERED`).
- `POST /recordatorios/ejecutar` existe porque **Render free duerme la instancia** y un
  `@Scheduled` interno no corre de forma fiable. Es idempotente: puede dispararse desde
  `cron-job.org` o un Render Cron Job cada hora; el job decide si son las 09:00 y si ya envió.
  Sin `X-Cron-Secret` válido → `403 PROHIBIDO`.
- El token FCM **no** se devuelve completo en el listado: `tokenEnmascarado` (primeros 8 y
  últimos 4 caracteres) para que un volcado de logs o una captura no expongan la credencial.

DTOs nuevos en `dto/`:

```
DispositivoPushRequestDTO   { token @NotBlank @Size(max=255), plataforma @NotNull }
DispositivoPushResponseDTO  { id, plataforma, activo, fechaRegistro, tokenEnmascarado }
DispositivoPushBajaDTO      { token @NotBlank }
ResultadoRecordatoriosDTO   { evaluados, enviados, omitidos }
```

## 5. Servicios

### `PushSender` (interfaz, paquete `service/push`)

```java
void enviar(String token, String titulo, String cuerpo, Map<String, String> datos);
```

Dos implementaciones, seleccionadas por propiedad:

- `FcmPushSender` — `firebase-admin`; requiere `app.push.log-only=false` y credenciales.
- `LogPushSender` — por defecto (`app.push.log-only=true`); loguea token enmascarado, título y
  cuerpo. Es lo que corre en dev, test y en el primer despliegue sin Firebase.

Errores de FCM: `UNREGISTERED` / `INVALID_ARGUMENT` → marcar `activo=false` (token muerto);
error de red → `WARN` y seguir con el resto de dispositivos (un fallo no cancela la corrida).

### `RecordatorioService`

1. Calcula `hoy = FechasMovimiento.hoy()`.
2. Busca deudas `PENDIENTE` con `fechaPrimeraCuota IS NOT NULL` (una consulta, sin N+1).
3. Para cada deuda, obtiene la **próxima cuota impaga** reutilizando la lógica de T3
   (`DeudaResponseDTO.proximaCuotaNumero/proximaFechaVencimiento` vía `DeudaService`, no se
   reimplementa la imputación).
4. Determina el tipo según la diferencia de días (`T-3`, `T0`, `T+1`). Fuera de esas ventanas
   no hay aviso.
5. Filtra los que ya están en `RECORDATORIO_ENVIADO`.
6. Agrupa por usuario, compone el texto y envía a sus dispositivos activos.
7. Persiste los `RECORDATORIO_ENVIADO` **solo si al menos un dispositivo aceptó el envío**; si todos los tokens del
   usuario fallan, no persiste nada y se reintenta en la próxima corrida (nota de §11: el envío ocurre dentro de la
   transacción del job, así que bitácora y resultado quedan consistentes).

Regla de horario (refuerzo de D4): el job **no evalúa ni envía nada fuera de la ventana [08:00, 22:00) en
America/Santiago**. La ventana está defendida en código (`RecordatorioService.ejecutar`), no solo en el horario del
cron, de modo que un cron externo disparando cada hora (§4) no pueda emitir pushes de madrugada.

Textos (español, sin jerga financiera):

- 1 cuota: `"Cuota 3 de «Notebook» vence en 3 días"` / `"…vence hoy"` / `"…venció ayer"`.
- N cuotas: `"Tienes 3 cuotas por vencer"` / `"…que vencen hoy"` / `"…vencidas"`.
- Payload `data`: `{"tipo":"RECORDATORIO_CUOTA","deudaId":"77","cuota":3,"deepLink":"saveup://deudas/77"}`.

### `NotificacionScheduler`

`@EnableScheduling` en una clase de configuración (`config/SchedulingConfig`) y:

```java
@Scheduled(cron = "0 0 9 * * *", zone = "America/Santiago")
public void recordatoriosDiarios() { ... }
```

El scheduler y el endpoint manual llaman al mismo `RecordatorioService.ejecutar()`. El
`scheduled` debe ser *no-op* si `app.push.habilitado=false` (permite apagar la feature sin
desplegar código).

## 6. Propiedades nuevas

```properties
# --- T9.6: notificaciones push ---
app.push.habilitado=true
# true = no envía a FCM, solo loguea (dev/test/sin credenciales)
app.push.log-only=true
# Días de antelación del aviso PROXIMA_VENCER
app.push.dias-antes=3
# Secreto del trigger manual POST /notificaciones/recordatorios/ejecutar
app.push.cron-secret=${PUSH_CRON_SECRET:}
# Credenciales del service account de Firebase (JSON en base64). Vacío = log-only.
FIREBASE_CREDENTIALS=
```

En `application-prod.properties`: `app.push.log-only=false` cuando existan credenciales;
mientras no existan, dejar `true` para no romper el job.

## 7. Dependencias

`com.google.firebase:firebase-admin` — **solo si se aprueba D1**. Añade ~15 MB al jar y una

## 8. Pruebas

- `RecordatorioServiceTest`: ventanas T-3/T0/T+1, fuera de ventana, deuda sin

## 9. Decisiones (aprobadas)

1. **D1 — FCM** para Android e iOS (no APNs directo).
2. **D3 — una push por usuario y corrida** (no una por deuda).
3. **D2 — T-3 / T-0 / T+1**.
4. **Alcance** — implementación completa antes del frontend, con `firebase-admin` y
   `app.push.log-only=true` por defecto (funciona sin credenciales).

Notas de implementación que no estaban en la spec:

- Ajustes post-revisión (oct 2026): (a) la ventana de horario D4 vive defendida en código — `ejecutar()` no evalúa ni
  envía nada fuera de [08:00, 22:00) Santiago, con retorno no-op (0,0,0) — para blindar el trigger horario de §4;
  (b) el texto plural de mezcla usa el aprobado en §5 ("Tienes N cuotas que vencen hoy"); (c) si una deuda se elimina
  mientras la push vuela, no se persiste su recordatorio (log INFO) y la corrida no falla; (d) `RecordatorioService`
  reutiliza `DeudaService.obtenerDeudasPorUsuario(rut)` (una consulta por usuario con dispositivos activos;
  aceptable al volumen del MVP y a revisar si crece) para no duplicar la imputación de pagos de T3.
- El envío ocurre dentro de la transacción del job para que deduplicación y resultado sean
  consistentes. Si el número de dispositivos crece, separar cálculo, envío y persistencia.
- `POST /dispositivos` documenta **200 y 201** en OpenAPI (upsert); el `DELETE` documenta **204**.
- Desviación consciente de §4: el trigger de cron es la única ruta sin JWT (usa `X-Cron-Secret`).
- El endpoint de cron queda **cerrado (403)** si `PUSH_CRON_SECRET` no está definido.
